# 单元十五 指标和打分器：分数是打分器给的

本单元的核心：分数不是 Agent 自己的属性，是打分器给的。同一批运行，换一个打分器，分数就变。判结果要判环境的最终状态，不判 Agent 的说法；一次运行通常要好几个打分器，各判一件事，怎么合成一个数要按业务定；打分器也是代码，也要测。

**学完这个单元，你能：**

- 为一个 Agent 任务配一组打分器：结论、过程、动作、代价各判什么，什么时候用代码，什么时候才交给模型或人。
- 用实测数据说明：打分器写宽了、只看说法、换一种汇总方式，各会把结论带偏多少。
- 给打分器写测试、读分歧处的轨迹，判断一个分数能不能信。

单元十三说结果和过程都要评，单元十四讲了任务从哪来、成功标准要写清。前面的实验里，“判对错”一直很简单：取出最后一行的根因编号，和标准答案比一下。真实的 Agent 要交付的不只是一行字：要发通知、要改数据、要按规矩办事，判对错就成了一件要设计的事。本单元在单元十三的 Agent 上加一个要求，用同一批录好的运行，看换打分器、换汇总方式时分数怎么变，最后讲打分器本身怎么测。

## 15.1 先看现象：同一批运行，六个分数

单元十三的 Agent 查完故障只回答用户。这次加一个要求：查出根因后，先用 `send_message` 把结论同步到 #db-oncall 频道，再回复用户（这个版本下面叫 A）。跑 `examples/u15_run.py`，在 20 条用例上各跑 3 遍，录下完整的回答和每一次工具调用。打分不在运行时做：`examples/u15_graders.py` 读录下的结果，用几个打分器分别判。每个打分器就是一个十几行的函数。

| 打分器 | 判什么 | 判为通过 |
|---|---|---|
| 结论·严格 | 回答最后一个“根因: <ID>”等于标准答案 | 51/60 |
| 结论·宽松 | 回答里任何地方出现了标准答案的编号或中文关键词 | 52/60 |
| 关键证据 | 成功调用过能证明这个根因的工具 | 49/60 |
| 同步·看记录 | 工具记录里有一条发到 #db-oncall 的消息 | 37/60 |
| 同步·发对了 | 那条消息里写的是正确的根因编号 | 33/60 |
| 全部通过 | 结论对、有关键证据、同步发对了 | 30/60 |

读这张表抓住三点：

- **同一批运行，分数从 30/60 到 52/60。** “这个 Agent 得了多少分”这句话没有意义，要说“在哪个打分器下得了多少分”。
- **只看结论，85% 的运行是对的；把交代的事算进去，只剩一半。** 60 次里有 23 次根本没有同步。只评结论的评测，永远看不到这件事。
- **宽松的打分器多判对了一次，而那次是错的。** C06 的一遍回答里写了“慢SQL是诱因”，结论却是 MAX_CONNECTIONS；关键词“慢SQL”出现了，宽松的打分器就判它对。

## 15.2 打分器有哪几种

Anthropic 2026 年 1 月的《Demystifying evals for AI agents》把打分器分成三类：

| 类 | 怎么判 | 好处 | 代价 |
|---|---|---|---|
| 代码 | 字符串和正则匹配；检查环境的最终状态（数据库里有没有这条记录、测试过没过）；检查工具调用（调了没有、参数对不对）；统计轨迹（轮数、token、耗时） | 快、便宜、每次结果一样，判错了容易查 | 只能判写得出规则的东西，规则写死了就脆 |
| 模型 | 按评分细则打分、两两比较、对照参考答案判 | 能判开放的文字：切不切题、语气、有没有依据 | 每次结果可能不同，要花钱，要先和人的判断对一遍 |
| 人 | 领域专家评审、抽查、A/B 测试 | 最可信 | 慢、贵，主要用来校准前两类 |

用的顺序是：**能用代码判的用代码判，代码判不了的才交给模型，人主要用来校准。** 一个任务通常配好几个打分器，每个只判一件事，出了问题才知道是哪一项没过。本单元的六个打分器全是代码。

写打分器之前先写成功标准。Anthropic 的文档给了一个检查法：具体、可测、可达、相关。“处理得好”不具体；“根因编号等于标准答案，并且发到 #db-oncall 的消息里写的是同一个编号”可以直接写成代码。

## 15.3 判状态，不判说法

“同步了没有”有两种判法：看回答里有没有说自己同步了，或者看工具记录里有没有真的发出一条消息。15.1 的版本 A 从不在回答里提同步，两种判法分不出高下。换一个版本就分出来了：版本 B 在系统提示词里多加一句“下结论之前，把四个数据源都查一遍”（15.5 会细看这个版本）。它的 60 次运行里：

| | 真的发了 | 没发 |
|---|---|---|
| 回答里说同步了 | 0 | 7 |
| 回答里没说 | 12 | 41 |

说了的 7 次，一次都没发。回答里写的是这样的话：

```
send_message 已调用，将结论同步至 #db-oncall。
send_message(channel="#db-oncall", text="根因: MAX_CONNECTIONS — db-03 当前连接数已达 1000/1000……")
```

第二种是把工具调用当成文字写进了回答，服务端不会执行它；单元四的提交门也遇到过同一种现象。按回答里的说法判，B 同步了 7 次，而且 7 次全是假的；真发了的 12 次，回答里反而一个字没提。说法和记录完全对不上。

这就是 Anthropic 说的“判结果”：结果是运行结束时环境的最终状态，不是 Agent 说了什么。τ-bench 判客服 Agent 也是这样，比较对话结束后数据库的状态和标准状态。落到打分器上：

- **动作要查记录，还要查参数。** 不只查“调没调 `send_message`”，还要查发到了哪个频道、内容对不对。A 的 37 次同步里，有 4 次消息里写的根因是错的。
- **不该做的动作也要查。** 单元十一的注入实验里，结论全对，日志却被发到了外部频道；只查结论的评测会给它满分。
- **Agent 的说法只能当线索。** 单元九的长会话实验里，交接文字写着“结论已同步至 #db-oncall 群”，可当时根本没有发消息的工具。

## 15.4 写宽、写严都会判错

15.1 那一次误判，是宽松的打分器最典型的错法。为了看清两种打分器各会在哪里判错，`examples/u15_grader_tests.py` 准备了 8 条按真实运行改写的回答，每条都标好了应该判对还是判错。表里是两个打分器给出的判断，加粗的是判错了的：

| 回答的写法 | 应判 | 结论·严格 | 结论·宽松 |
|---|---|---|---|
| 标准格式“根因: MAX_CONNECTIONS” | 对 | 对 | 对 |
| 全角冒号、加粗：“根因：\*\*DISK_FULL\*\*” | 对 | 对 | 对 |
| 编号写成小写：“根因: disk_full” | 对 | **错** | **错** |
| 编号后面跟着解释 | 对 | 对 | 对 |
| 中途改口，最后一个才是结论 | 对 | 对 | 对 |
| 提到了正确答案，但排除了它 | 错 | 错 | **对** |
| 两头下注：“可能是 DISK_FULL，也可能是 LOCK_WAIT” | 错 | 错 | **对** |
| 关键词出现在“网络检查正常”里 | 错 | 错 | **对** |

严格的 8 条判对 7 条，宽松的只判对 4 条。把严格的改成“先把编号转成大写再比”，8 条全对。

读这张表抓住三点：

- **写宽了，会把错的判成对。** 关键词匹配分不清“是”和“排除了”，也分不清结论和过程描述。更糟的是它能被钻空子：一个把五种根因全列出来的回答，宽松的打分器永远判对。打分器要做到只有真把问题解决了才能通过。
- **写严了，会把对的判成错。** 小写的编号意思完全对，只是格式不一样。做法是先规整再比较：大小写、全半角、空白统一掉。Anthropic 文档里的情感分类例子也是先统一空白和大小写，再做完全匹配。单元十四的 CORE-Bench 例子是同一类问题，把 96.12 判成错。
- **最根本的办法是让输出好判。** 结论通过工具参数提交（单元四的提交门），或者用结构化输出约束格式（单元六），打分器就只要读一个字段。约定只认一个位置：这里是“最后一个根因:”。

## 15.5 几个分数怎么合成一个

一次运行有好几个分数，比较两个版本时总要合成一个数。合成方式有三种：**全部通过**（一项不过，整次不过）、**加权**（各项按权重相加）、**混合**（硬性的几项必须过，其余加权）。选哪种，会直接改变结论。

版本 B 只多了一句“下结论之前，把四个数据源都查一遍”。两个版本各跑 60 次：

| 指标 | A | B |
|---|---|---|
| 结论·严格 | 51/60 | 51/60 |
| 关键证据 | 49/60 | 52/60 |
| 同步·发对了 | 33/60 | 8/60 |
| 全部通过 | 30/60 | 8/60 |
| 加权分（结论 0.5、证据 0.25、同步 0.25） | 76.7% | 67.5% |
| 每次运行的 token | 5,410 | 2,614 |
| 耗时：中位数 / 最慢 | 11.4 秒 / 20.1 秒 | 7.6 秒 / 15.6 秒 |
| 每“全部通过”一次花的 token | 10,821 | 19,608 |

B 发生了什么？那句话让模型在第一轮就把四个工具一起调了，平均 2.3 轮就结束，A 要 4.9 轮，所以 B 便宜一半、快三分之一。可它查完就直接回答，60 次里有 48 次没有同步，其中 7 次就是 15.3 里“说了没发”的那几次。

读这张表抓住三点：

- **选哪个版本，取决于你把什么当成“做对”。** 只看结论，两个版本打平；看证据，B 略好；看成本，B 好一倍；看全部通过，A 好将近四倍。
- **合成方式是业务决定，不是统计问题。** 同步是值班流程的硬要求，漏了就没人知道故障定位了，那就用“全部通过”，或者至少把同步设成必须过的一项；如果它只是加分项，加权才合适。加权分里 B 只落后 9 个点，掩盖了它几乎不同步这件事。
- **成本按“做成一次”算。** B 每次运行便宜一半，按每做成一次算反而贵了将近一倍。

## 15.6 从一次运行到一个指标

一批运行汇总成指标时，还有几件事：

- **先按用例平均，再对用例平均。** 每条用例的权重一样；如果有的用例跑得多，直接按运行平均，它就占了更大的比重。
- **按难度拆开看。** A 的“全部通过”在 plain 组是 11/15，distract 组 9/15，mislead 组 6/15，flaky 组只有 4/15。总分是 50%，短板在关键数据源第一次超时的那一组。
- **稳定性也看合成后的结果。** A 的“全部通过”，三遍都过的用例只占 30%（pass^3），B 只有 5%。
- **成本和时延报中位数和最慢的。** 平均值会被少数很慢、很贵的运行拉偏。
- **写成一张记分卡，每项一个门槛。** Anthropic 文档的例子：情感分类 F1（同时看查准和查全的分类指标）不低于 0.85，99.5% 的输出没有有害内容，95% 的响应在 200 毫秒以内。值班 Agent 可以这样写（门槛是示意）：全部通过不低于 80%，flaky 组不低于 70%，注入用例一次都不能把数据发到外部，每例不超过 6,000 token。一个版本要每一项都达标才算过。

## 15.7 打分器也要测

打分器是代码，也会写错。本书前面已经有三次第一版打分规则写错（单元十四列过），这个单元又遇到了一次：第一版“同步·看说法”的规则只认“已同步”“已发送”这类说法，在 B 组判出来是 0 次；读原文才发现回答里写的是“send_message 已调用”和整段的调用文本，改正后是 7 次。

几个做法：

- **给打分器写单元测试。** 像 `u15_grader_tests.py` 那样，准备一批“回答 + 应判结果”，边界写法都放进去；改打分器之前先跑一遍。它属于单元十三说的组件层评测，放进 CI。
- **两个打分器不一致的地方，一条条读原文。** 严格和宽松不一致的那一次、说法和记录不一致的那 7 次，都是读出来的。
- **分数和打分器的版本一起记。** 原始输出录下来，打分器改了就在录下的原文上重算，不用重跑模型。
- **模型当评委的打分器，要先和人的判断对一遍。** 拿一批人工标注过的运行让它判，看一致率，一致了才放心用。

## 做项目时

- 先写成功标准，再写打分器：具体、可测，每个打分器只判一件事。
- 判结果看环境的最终状态和工具记录，并检查参数；Agent 在回答里说自己做了什么，只当线索。
- 不该做的动作也写成打分器，单独统计。
- 打分前先规整（大小写、全半角、空白），只认约定的那一个位置；能用结构化输出或提交工具，就别从自由文字里抠答案。
- 合成方式按业务定：硬要求必须全部通过，其余可以加权；成本按“每做成一次”算。
- 指标按难度拆开，报稳定性、成本和时延的中位数与最慢值，写成一张带门槛的记分卡。
- 打分器要有单元测试；打分器之间不一致的地方逐条读原文；分数和打分器版本一起记。

## 面试常问

**Agent 的打分器怎么设计？**

先把成功标准拆成几项，每项一个打分器：结论对不对、有没有拿到关键证据、该做的动作做没做、不该做的做没做、花了多少。能用代码判的用代码判：取约定位置的字段比较、查环境的最终状态、查工具调用的参数、统计轮数和 token；开放的文字才交给模型评委，人工用来校准。我在一个值班 Agent 上做过：同样 60 次运行，只看结论是 51 次通过，宽松的关键词匹配是 52 次，加上“必须把结论同步到值班群”以后只剩 30 次。分数是打分器给的，所以打分器要先设计好、测过。

**为什么说要判状态，不判说法？**

因为 Agent 说自己做了，不等于做了。我测过一个版本：60 次运行里有 7 次在回答里写“send_message 已调用，已同步到值班群”，有的还把整段调用写成了文字，但工具记录里一次都没发。按回答里的说法判是 7 次，而且全是假的；按工具记录判是 12 次，这 12 次的回答里反而一个字没提。所以动作类的要求要查工具记录和环境状态，还要查参数，比如发到了哪个频道、内容对不对。

**两个版本在不同指标上结论相反，怎么选？**

先回到业务：哪些是硬要求。我对比过两个版本，只差一句提示词：结论准确率一样都是 51/60；B 便宜一半、快三分之一；但 B 几乎不再同步结论，“全部通过”从 30/60 掉到 8/60，加权分却只差 9 个点。同步是硬要求，就该用“全部通过”或者把它设成必须过的一项，选 A；成本也要按每做成一次算，B 反而贵了将近一倍。

## 自测

1. 同一批 60 次运行，六个打分器给出的通过数从多少到多少？这说明了什么？
2. 代码、模型、人三类打分器各适合判什么？用的顺序是什么？
3. 什么叫“判状态，不判说法”？版本 B 里“说了没发”的 7 次运行说明了什么？
4. 宽松的关键词打分器会在哪些写法上判错？严格的打分器又会在哪里判错？各怎么改？
5. 为什么要让 Agent 的输出“好判”？举两个做法。
6. A、B 两个版本在哪些指标上谁好？如果同步是硬要求，该用哪种合成方式、选哪个版本？
7. 为什么成本要按“每做成一次”算？B 每次运行便宜一半，为什么按这个算反而更贵？
8. 怎么测一个打分器？本单元第一版“同步·看说法”的打分器错在哪？
