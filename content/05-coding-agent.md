# 单元五 解剖一个 Coding Agent：从三十行循环到 Claude Code

本单元的核心：Claude Code 这样的编程 Agent，就是单元三的循环加上单元四的 harness，再为“长时间改一个代码仓库”加上几样机制：好用的文件工具、计划、子 Agent、技能、上下文压缩、记忆、外部工具接入。每一样都是为了解决长任务里的一个具体问题，也都有代价。

**学完这个单元，你能：**

- 列出一个编程 Agent 的组成，说出每个机制要解决的问题、挂在循环的哪个位置。
- 用实验数据讲清三个设计：改文件为什么用字符串替换，子 Agent 省了什么、多花了什么，技能为什么按需加载。
- 回答“Claude Code 是怎么工作的”，并说出 pi 在同样的问题上为什么选择不做。

单元四在迷你值班现场上挂了三个机制，任务只有几轮。编程 Agent 的任务长得多：几十上百轮、面对整个代码仓库、要改文件和跑命令。长任务会暴露短任务里看不到的问题：改一个文件要花多少输出、上下文被读过的文件塞满、做着做着忘了目标、项目的规矩每次都要重新交代。本单元按 learn-claude-code 的顺序，把一个编程 Agent 的机制一样一样拼出来，每一样都说清楚它解决什么、pi 怎么看。先看全貌，再逐个看几个关键机制，最后把第一部分串起来。

## 5.1 全貌

learn-claude-code 把 Claude Code 拆成十七章，每章在同一个循环上加一个机制，循环本身一行不改：

| 机制 | 解决什么问题 | learn-claude-code | 挂在哪 |
|---|---|---|---|
| 循环 | 模型说完就停，不会接着干 | s01 | 循环本身 |
| 工具分发 | 只有 bash 时，读写文件都要拼命令 | s02 | 执行 |
| 权限 | 模型能跑 `rm -rf` | s03 | 执行前 |
| hooks | 每加一个功能都要改循环 | s04 | 四个位置都开放 |
| 待办清单 | 长任务做着做着忘了目标 | s05 | 一个工具 + 执行后的提醒 |
| 子 Agent | 探索过程把主上下文塞满 | s06 | 一个工具，里面另起一个循环 |
| 技能 | 规范文档全塞进系统提示词，每轮都付钱 | s07 | 组装上下文 + 一个工具 |
| 上下文压缩 | 上下文迟早会满 | s08 | 组装上下文 |
| 记忆 | 新会话不记得上次学到的东西 | s09 | 组装上下文 + 会话结束时 |
| 任务系统 | 待办清单没有依赖关系，也不能跨会话 | s10 | 一组工具 + 磁盘上的文件 |
| 后台任务、定时任务 | 慢命令卡住循环；没人触发就不干活 | s11、s12 | 循环外的线程，完成后往上下文里插通知 |
| 团队协作 | 一个 Agent 忙不过来 | s13 | 多个循环，通过任务和消息协调 |
| MCP | 每接一个外部系统都要手写工具 | s14 | 工具池 |
| 编排脚本、目标循环 | 固定的多步编排；“真的做完了吗” | s16、s17 | 一个工具；想结束时 |

读这张表抓住三点：

- **每一行都是“问题 → 机制”，没有一行是“因为别人有所以我也加”。** 讲自己的项目时也要这样讲。
- **大部分机制都挂在单元四那四个位置上，**或者本身就是一个工具。工具是扩展 harness 最便宜的方式：模型自己决定什么时候用。
- **pi 只做了前几行。** 它有循环、四个工具、钩子、压缩和技能，待办、子 Agent、MCP 都留给扩展。下面讲到每个机制时，都会说一句 pi 为什么不做。

## 5.2 文件工具：为什么改文件用字符串替换

编程 Agent 最常做的事是改文件。最直接的工具是 `write_file(path, content)`：读出文件，让模型写出改好的完整文件。Claude Code 和 pi 都没这么做，它们的改文件工具都是字符串替换：给出一段原文和替换后的文字，原文必须在文件里恰好出现一次。

跑 `examples/u05_edit.py`。被改的是一个 169 行的库存服务（`examples/mini_repo/inventory.py`），任务是把 `reserve_stock` 的预占超时从 3 秒改成 5 秒，并在超时抛异常前打一条 warning 日志，其他代码不要动。两种工具各跑 3 遍，每遍在临时目录里改一份副本：

| | 完全做对 | 每遍输出 | 每遍耗时 | `reserve_stock` 之外被改动 |
|---|---|---|---|---|
| 读 + 重写整个文件 | 0/3 | 2,204 token | 51 秒 | 每遍 3 行 |
| 读 + 字符串替换 | 3/3 | 771 token | 18 秒 | 0 行 |

两组都完成了要求的两处修改，文件也都能正常解析。重写组的 3 行“额外改动”是什么？重跑一遍看 diff：模型把文件里所有文档字符串的三个双引号换成了三个单引号。整个文件要作为一个 JSON 字符串参数写出来，双引号要转义，模型大概是为了省事换了引号。这次碰巧不影响运行，但用户要求“其他代码不要动”，它还是动了。

读这张表抓住三点：

- **重写整个文件，等于让模型把没改的部分再抄一遍。** 输出是字符串替换的近三倍，耗时也是近三倍（单元一看到，耗时由输出长度决定）。文件越大差距越大：一个两千行的文件，改一行也要写出两千行。
- **抄的时候会顺手改。** 引号、空行、缩进、注释，模型在重写时会按自己的习惯“整理”，这些改动混在 diff 里，审查时很难一眼看出哪些是真正要改的。更糟的情况是漏抄几行，或者输出被截断，文件就坏了。
- **字符串替换把“改哪里”变成了程序能检查的事。** 原文必须逐字匹配、恰好一次，匹配不上就报错，模型只能先读文件再改。代价是模型要准确地复述原文，这也是 Claude Code 要求“改之前先读过这个文件”的原因。

这一组也说明了编程 Agent 工具设计的思路：pi 只给读、写、改文件和 bash 四个工具，搜索、跑测试、看 git 历史都让模型用 bash 去调现成的命令行程序。bash 是一个“万能工具”，模型在训练里见过大量命令行用法；专门的工具（比如 Claude Code 的搜索工具）则可以控制输出的长度和格式，省 token、少出错。

## 5.3 计划：待办清单

learn-claude-code 用一个例子说明问题：让 Agent “把所有 Python 文件改成 snake_case，然后跑测试、修好失败的”。改了三个文件、跑测试、发现两个失败，开始修；修着修着，注意力全被测试失败吸走，忘了还有文件没改。对话越长越严重：工具结果不断填满上下文，最初的目标在输入里越来越靠前、越来越不显眼。

Claude Code 的做法是给模型一个 `TodoWrite` 工具：每次调用把整张待办清单（每项一个内容和一个状态）写一遍。这个工具不做任何实际的事，它的作用是让目标和进度**反复出现在上下文的最新位置**。learn-claude-code 还加了一个提醒：连续三轮没更新清单，harness 就在工具结果后面追加一句提醒。

pi 不内置待办，理由是它会把模型搞糊涂，建议需要时让模型写一个 `TODO.md` 文件。两种做法的本质一样：把计划写在模型每一轮都看得到、而且是最新的地方。区别是谁来保证它被更新：一个是 harness 提醒，一个是靠模型自觉。

任务长到一个上下文窗口装不下、要跨好几个会话时，计划还得能交接。Anthropic 2025 年 11 月的《Effective harnesses for long-running agents》给了一个做法：

- **第一个会话只搭环境。** 一份功能清单（JSON，他们的例子里有两百多项，每项带一个“是否通过”的字段，初始都是否）、一个进度文件、一个启动脚本，再做第一次 git 提交。
- **之后每个会话先接班，再干活。** 读 git 日志和进度文件，跑一遍基本的端到端检查；上一班留下了坏掉的东西就先修。然后只挑一项没完成的功能做，做完验证、提交、更新进度，只允许改“是否通过”那一个字段。

两个“Agent”用的是同一套 harness，区别只在第一句提示词。这么做挡住的是他们观察到的几种失败：做了一点就宣布完成、留下改了一半的代码、没有端到端验证就标记完成、每次都花时间琢磨怎么启动项目。功能清单用 JSON 而不是 Markdown，是因为模型不太会乱改 JSON 的结构。

## 5.4 子 Agent：给子任务一段干净的上下文

编程 Agent 修一个 bug，常常要先读十几个文件弄清调用链。弄清之后，那些文件内容大部分不再需要，却一直留在上下文里，每轮重发。子 Agent 的做法（learn-claude-code s06）：父 Agent 调用一个工具，比如 `task(说明)`，程序另起一个**全新的循环**，从空白的 messages 开始做这个子任务；子 Agent 做完，只把最后的结论文字作为工具结果交回父 Agent，中间过程留在子 Agent 那里，随它一起丢掉。

在门缝的比方里：屋里的专家不再亲自翻每一摞材料，而是派一个助手去另一间屋子查，查完只递回一张写着结论的纸条。

跑 `examples/u05_subagent.py`。问题是“这 4 台库都有用户报问题，逐台查一下各自的根因”。两种做法：单个 Agent 自己查；主 Agent 只有一个 `investigate(instance)` 工具，每台交给一个子 Agent。两种现场：干净的（每个工具结果都很短），嘈杂的（错误日志不分页，每台前面多了 300 行无关告警）。各跑 3 遍：

| 现场 | 做法 | 答对 | 主 Agent 上下文峰值 | 所有 Agent 合计调模型 | 合计 token |
|---|---|---|---|---|---|
| 干净 | 单个 Agent | 12/12 | 1,938 | 3.3 次 | 4,264 |
| 干净 | 主 + 子 Agent | 12/12 | 1,023 | 14.0 次 | 10,593 |
| 嘈杂 | 单个 Agent | 12/12 | 79,014 | 4.0 次 | 82,405 |
| 嘈杂 | 主 + 子 Agent | 12/12 | 1,596 | 10.0 次 | 85,517 |

“上下文峰值”是一次调用里最大的输入：它决定会不会撑爆上下文窗口。嘈杂现场里，每个子 Agent 自己的峰值约两万 token。

读这张表抓住三点：

- **子 Agent 省的是单个上下文的峰值，不是总花费。** 干净现场里，用子 Agent 多花了 2.5 倍的 token、4 倍的调用，只换来主 Agent 峰值少了几百 token，不划算。
- **中间过程很长时，它才值得。** 嘈杂现场里，单个 Agent 一次把 4 份刷屏日志都读进来，峰值近八万 token，再多几台库就会撑爆窗口；用子 Agent 后总花费差不多，主 Agent 的峰值只有一千多，每个子 Agent 也只有两万。
- **能在源头变小的，先在源头变小。** 嘈杂现场的根本问题是工具结果太长。单元四的“合并重复行”把一份日志从近六万字符变成两百多字符，比派子 Agent 便宜得多。子 Agent 适合另一类情况：中间材料是真的要读的（读源码、读网页），只是读完以后不再需要。

还有两点 learn-claude-code 特别强调：

- **子 Agent 隔离的是上下文，不是权限和环境。** 它和父 Agent 共用同一个工作目录，写的文件、跑的命令照样生效。所以权限检查不能因为是子 Agent 就省掉。
- **子 Agent 不能再派子 Agent。** learn-claude-code 的子 Agent 没有 `task` 工具，避免无限嵌套。

pi 不内置子 Agent，理由是“做法有很多种”：可以在另一个终端窗口里再开一个 pi，也可以用扩展自己写。

## 5.5 技能：先给目录，用到再加载

项目有 React 组件规范、SQL 风格指南、API 设计文档，希望 Agent 遵守。最直接的做法是全部拼进系统提示词，但那样每一轮都要把所有文档发一遍，不管这次任务用不用得上。**技能**（Skills）的做法是渐进披露：系统提示词里只放一份目录，每份技能一个名字加一句描述；模型判断需要时，再调用工具读全文（learn-claude-code s07）。每份技能是一个目录，里面一个 `SKILL.md`，开头几行写名字和描述。Claude Code 和 pi 都支持这种格式。Anthropic 2025 年 10 月的文章把加载分成三层：名字和描述常驻系统提示词；判断用得上时读 `SKILL.md` 正文；正文里再引用的文件和脚本，用到时才读，脚本还可以直接运行、源码不进上下文。同年 12 月，这个格式作为开放标准（Agent Skills）发布。

迷你现场里放了 5 份排查手册（`examples/mini_skills/`），每份讲一种根因怎么查、容易和什么混淆、结论要什么证据，合计 2,469 个字。跑 `examples/u05_skills.py`，两种做法，4 个场景各跑 2 遍：

| | 答对 | 每次调用平均输入 | 每例累计输入 | 读了几份手册 |
|---|---|---|---|---|
| 全部塞进系统提示词 | 8/8 | 2,045 token | 5,879 token | 不需要读 |
| 只放目录，按需加载 | 8/8 | 939 token | 2,818 token | 8 例里 0 份 |

输入少了一半多，答对的一样多。但按需加载的那组，一份手册都没读：这 4 个场景对它来说不难，它觉得用不上。

那手册真正派得上用场时呢？再跑一个情况：S4 的工具全部超时（和单元三的实验一样），提示词仍然要求根因五选一，而 network 手册里写着“只有排除法时，结论应写 UNKNOWN 并说明还缺什么”。各跑 5 遍：

| | 给出的根因 | 读了几份手册 |
|---|---|---|
| 不给手册 | DISK_FULL ×2，NETWORK ×3 | |
| 全部塞进系统提示词 | UNKNOWN ×2，DISK_FULL ×3 | |
| 只放目录，按需加载 | DISK_FULL ×5 | 0 份 |

读这两张表抓住三点：

- **按需加载省的是“用不上的知识”的钱。** 5 份手册就让每次调用多出一千多 token；技能有几十份时，全塞进去根本放不下。
- **按需加载多了一种失败：模型没想到要读。** 它是看目录里那一句描述来决定读不读的，就像看工具描述决定调不调。这次它直接按“写入失败、读正常”猜了磁盘写满，没有去看讲“排除法”的那份手册。所以技能的描述要写清“什么情况下该读我”，而不只是“我讲什么”。pi 的文档里也提醒，模型不一定会去读，必要时用 `/skill:名字` 强制加载。
- **必须遵守的规则，不能只放在知识里。** 即使把手册全塞进去，5 遍里也只有 2 遍照着做了。“没有证据不下结论”这样的底线，应该像单元四的提交门那样由程序检查。分工是：怎么查（知识）放进技能，按需读取；底线（规则）放进 harness，每次都执行。

Anthropic 给的建议也是同一个方向：先跑评测，找出 Agent 做不好的地方，再一份一份补技能；名字和描述要花最多心思，因为模型靠它们决定读不读。另外，技能里有指令也有脚本，只装可信来源的。

技能和工具的区别也在这里：工具让模型能**做**一件事，技能让模型**知道**一件事。pi 甚至主张用技能代替 MCP：把外部能力做成命令行程序，再写一份技能说明怎么用，模型读了说明后用 bash 去调。

## 5.6 上下文压缩和记忆

上面两个机制都是让上下文长得慢一点。但长任务的上下文迟早会满，满了要腾地方；会话结束，学到的东西还要留下来。

**压缩。** learn-claude-code 按“便宜的先做”排了四步：

| 步 | 做什么 | 花不花模型调用 |
|---|---|---|
| 1 | 最新一批工具结果总量太大时，把最大的几个存到文件里，上下文只留路径和开头一段 | 不花 |
| 2 | 消息超过 50 条，把完整历史存档，只保留最开头和最近的若干条 | 不花 |
| 3 | 上下文还是太长，把模型已经读过的旧工具结果换成文件路径，只留最近几条原文 | 不花 |
| 4 | 仍然超限，让模型把历史写成一份只含事实的状态摘要，替换掉旧消息 | 花一次 |

pi 只做第 4 步：快满时保留最近一段原文，更早的部分让模型写成结构化摘要；下次再压缩时，在上一份摘要的基础上更新。

Claude Code 的压缩是这样写的：保留架构上的决定、没解决的 bug 和实现细节，丢掉重复的工具输出，再把最近访问的 5 个文件重新读进来（Anthropic 2025 年 9 月《Effective context engineering》）。

两者的共同点是：**压缩会丢信息**，所以先做不丢信息的（存文件、留路径，需要时还能读回来），最后才让模型写摘要。压缩之外还有一种更彻底的做法：清空上下文，让一个新的 Agent 读交接文件接着做，代价是多一套交接的编排；单元四说过，需不需要这样做取决于模型。单元四的“合并重复行”也是同一类：在结果进上下文之前就把它变小。

**记忆。** 有两种：

- **人写的**：项目根目录的 `CLAUDE.md`、`AGENTS.md`，写项目的规矩、常用命令、注意事项。harness 启动时把它整个放进系统提示词（pi 也读这两个文件）。它每轮都在，所以要短。
- **Agent 自己攒的**：会话中学到的、以后还用得上的信息（用户的偏好、项目里不明显的约定），一条一个文件，再维护一个索引。新会话时只把索引放进上下文，需要时再读具体的一条；会话结束时提取新的，定期合并重复、删掉过期的。Claude Code 的自动记忆就是这样：索引文件 `MEMORY.md` 每次会话只加载前 200 行或 25KB。learn-claude-code 的 s09 讲的就是这四件事：存储、召回、提取、整理。

技能和记忆长得很像（索引 + 按需读全文），区别是来源：技能是人写好的、只读的说明书，记忆是 Agent 从对话里攒下来的、会变的事实。

## 5.7 外部工具和协作

**MCP。** 每接一个外部系统（文档库、部署平台、数据库）都手写工具，很快就写不过来。MCP 是 Anthropic 2024 年 11 月发布的开放协议，把这件事拆成两个角色：MCP 服务器提供工具列表和调用入口，harness 负责连接、给工具加前缀避免重名、做权限检查，再把这些工具放进同一个工具池交给模型。代价在单元二算过：工具定义每轮都要发，接几个服务器就是几十个工具。pi 不支持 MCP，主张把外部能力做成带 README 的命令行工具，模型读说明、用 bash 去调，只有用到时才花 token，和技能是同一个思路。

**任务系统和多 Agent 协作。** 待办清单只在当前会话里、没有依赖关系。任务一多、要跨会话、要分给几个 Agent，就需要任务系统：每个任务存成磁盘上的一个文件，有编号、状态、负责人，以及“要等哪些任务先完成”。多个 Agent 各自跑自己的循环，通过认领任务、互发消息协作；为了不互相改坏文件，每个任务可以在自己独立的工作目录（git worktree）里做。

**目标循环。** 单元三说过，“模型不再调工具”只代表它这一轮想停。learn-claude-code 的最后一章加了一个独立的判断器：另起一次模型调用，只看完成条件和对话记录，判断是不是真的做完了；没做完就把理由追加进去、继续循环。这和单元四的提交门是同一个位置（想结束时），区别是验收者：提交门用程序核对，判断器用另一个模型判断。能用程序判断的（测试通不通过、证据编号存不存在），优先用程序。为什么不让干活的模型自己验收？Anthropic 2026 年 3 月的文章观察到，模型给自己的成果打分普遍偏宽，单独调一个挑剔的评审，比让干活的模型学会自我批评容易。

## 5.8 把第一部分串起来

| 单元 | 现在你能说清 |
|---|---|
| 一 | 模型是按概率续写的零件：花钱花时间、不保证一样、不保证真实 |
| 二 | 模型只说要调什么，执行、校验都是你的代码；它会编参数 |
| 三 | Agent 是一个循环；什么时候用它而不是 Workflow；它停下来时交的东西要兜底 |
| 四 | harness 是模型以外的一切，机制挂在循环的四个位置上，管边界和验收 |
| 五 | 编程 Agent 的每个机制都对应长任务里的一个问题，也都有代价 |

到这里，“Claude Code 是怎么工作的”这个问题可以这样回答：一个循环，十几个工具，四个位置上的钩子和权限检查，再加上待办、子 Agent、技能、压缩、记忆、MCP 这几样为长任务准备的机制。第二部分会把其中几样（工具协议、多 Agent、上下文和记忆、安全）各自展开成一个单元。

## 做项目时

- 改文件用字符串替换，要求原文恰好出现一次；改之前必须先读过文件。
- 长任务给模型一个写计划的地方（待办工具或文件），并让它出现在上下文的最新位置。
- 中间材料要读、读完不再需要时，才用子 Agent；结果太长先想办法在源头压缩。子 Agent 的权限检查不能省。
- 知识做成技能按需加载，描述写清“什么时候该读我”；底线规则不放在技能里，放进程序。
- 上下文管理按“不丢信息的先做”排序：结果存文件留路径、去掉旧结果，最后才让模型写摘要。
- 项目说明文件（`AGENTS.md`、`CLAUDE.md`）每轮都在，要短；会变的、按需才用的东西放到别处。

## 面试常问

**Claude Code 是怎么工作的？**

核心是一个循环：把历史和工具定义发给模型，模型要工具就执行、结果追加回去、再调模型，直到它不再要工具。外面是 harness：十几个工具（读写改文件、搜索、bash、子 Agent、待办），执行前的权限检查和 hooks，再加上几样为长任务准备的机制：待办清单让目标留在上下文最新的位置，子 Agent 用一段全新的上下文去做探索、只带结论回来，技能先给目录、用到再读全文，上下文快满时自动压缩，项目说明文件和记忆让它跨会话记得规矩，MCP 接外部工具。每一样都对应长任务里的一个具体问题。

**为什么改文件用字符串替换，而不是让模型重写文件？**

我实测过：改一个 169 行文件里的两处，让模型重写整个文件，每遍输出 2,200 多个 token、51 秒，而且 3 遍都顺手把所有文档字符串的引号改了；字符串替换每遍 770 个 token、18 秒，3 遍都只改了该改的地方。重写等于让模型把没改的部分再抄一遍，又慢又贵，还会按自己的习惯“整理”代码。字符串替换要求原文逐字匹配、恰好一次，匹配不上就报错，“改哪里”变成了程序能检查的事。

**子 Agent 什么时候用？**

它省的是单个上下文的峰值，不是总花费。我实测查 4 台库：工具结果很短时，用子 Agent 多花 2.5 倍 token，只换来主 Agent 峰值少几百 token，不值得；每台的日志都刷屏时，总花费差不多，但单个 Agent 的峰值近八万 token，用子 Agent 后主 Agent 只有一千多。所以中间材料要读、读完不再需要、而且多到会撑爆上下文时才用；结果太长的，先在工具那一层压缩更便宜。还要记住它隔离的是上下文，不是权限。

**Skills 有什么用？有什么坑？**

把知识做成按需加载：系统提示词里只放名字和描述，需要时再读全文。我实测 5 份排查手册，按需加载让每次调用的输入少了一半多，准确率一样。坑是模型可能想不到去读：所有工具都超时的情况下，讲“排除法不能下结论”的那份手册它一次都没读，5 遍都猜了一个根因；全塞进提示词也只有 2 遍照做。所以描述要写清什么时候该读，必须遵守的底线规则放进程序，不放进技能。

1. 编程 Agent 在单元四的 harness 之外，还加了哪几样机制？各解决长任务里的什么问题？
