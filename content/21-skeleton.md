# 单元二十一 搭骨架：配置、存储、队列、网关、轨迹

本单元的核心：骨架要解决两件事：同一份记录被几处用，以及流量超过上游时怎么办。前者靠一份只追加的事件日志，恢复、轨迹、评测题都从它读；后者靠排队，并把 worker 数对齐上游的限额，重试解决不了过载。

**学完这个单元，你能：**

- 搭一个最小可用的 Agent 骨架：配置指纹、事件日志、任务表和租约、网关、worker 池，说清每一块解决什么问题。
- 用模拟数据说明为什么要排队、worker 数为什么要对齐上游的限额，以及为什么重试解决不了过载。
- 从同一份事件日志恢复任务、生成轨迹、导出评测题，并决定哪些内容进轨迹、哪些只留在日志里。

单元十二讲了运行时的几个机制：从事件日志恢复、幂等、模型网关、轨迹，每个都单独做了实验。单元二十定好了标准，下一步是把这些机制装进一个能跑的骨架。代码在 `examples/skeleton/`，只用标准库，几百行。先看骨架长什么样，再让它跑 20 个任务、中途崩掉一个 worker；然后模拟一次告警风暴，看队列为什么重要；最后讲配置、存储和轨迹里的几个决定。

## 21.1 骨架长什么样

| 部分 | 做什么 | 文件 |
|---|---|---|
| 配置 | 会改变输出的东西放在一处，算一个指纹 | `config.py` |
| 存储 | 一个 SQLite 文件三张表：配置、任务（状态和租约）、事件（只追加） | `store.py` |
| 网关 | 模型调用的并发上限、重试、用量，重试只在这里做 | `gateway.py` |
| 执行 | 从事件日志恢复，每一步先写事件再往下走 | `runner.py` |
| 队列 | worker 领任务、续租约；同一个会话同一时间只跑一个任务 | `worker.py` |
| 轨迹 | 从事件日志生成轨迹，用 OpenTelemetry 的命名，默认不带正文 | `trace.py` |
| 导出 | 跑完的任务变成评测题候选，脱敏 | `export.py` |

一个任务的路径：提交进任务表（排队中）→ 某个 worker 领走，拿到一个租约 → 读事件日志，恢复到上次停下的地方 → 循环里每次模型调用都经过网关，每次调用、每个工具结果都先追加进事件日志 → 写最后一条事件，把任务标成完成。轨迹和导出都只读事件日志。

**租约**是这里的关键：worker 领任务时写下“这个任务归我，到某个时间为止”，每走一步续一次。worker 死了就不会再续，租约一过期，任务又能被别的 worker 领走。数据库里一个字段，就把“谁在跑它”和“它是不是没人管了”两件事都记下了。

## 21.2 先看它跑：20 个任务，中途崩一个 worker

跑 `examples/u21_skeleton.py`。迷你评测集的 20 条问题作为 20 个任务提交，4 个 worker 执行。C01 和 C02、C11 和 C12 放在同一个会话里，像同一个用户连问两次。C05 执行到第二个工具结果写进日志之后，worker “崩溃”：任务状态不更新，停在“运行中”，等租约（8 秒）过期。

| | 结果 |
|---|---|
| 任务 | 20 个全部完成，答对 17 个；墙钟 59.5 秒 |
| 网关 | 80 次模型调用，没有限流，没有出错；每个任务 token 的中位数 4,092 |
| 同一会话 | C01 在 0 到 4.7 秒，C02 在 4.7 到 11.1 秒；C11 和 C12 也是一个结束、下一个才开始 |
| 崩溃的 C05 | 领取了 2 次，结论慢 SQL，答对了 |

C05 的事件日志：

| 序号 | 时间 | 事件 | 谁写的 |
|---|---|---|---|
| 0 | 0.0 秒 | 开始 | w1 |
| 1～2 | 2.4 秒 | 模型调用，查监控指标 | w1 |
| 3～4 | 4.5 秒 | 模型调用，查慢查询日志；随后 w1 崩溃 | w1 |
| 5 | 14.6 秒 | 恢复，接在第 4 条之后 | w4 |
| 6～9 | 17.3～18.2 秒 | 查错误日志，查网络 | w4 |
| 10～11 | 22.7 秒 | 模型下结论，结束 | w4 |

读这两张表抓住三点：

- **没有重复查数据。** w4 接手时，从事件日志重放了前两次工具结果，接着查第三个、第四个数据源，四个数据源各查了一次。单元十二说过，补执行的如果是有副作用的工具，要用“任务 ID + 动作”做幂等；这里都是只读查询，补执行也安全。
- **接手花了约 10 秒：8 秒租约，加上 worker 轮询的间隔。** 租约越短，接手越快；可是一步走得比租约还长（比如一次要写很长回复的模型调用），任务就会被误判成没人管，被第二个 worker 同时领走。所以租约要比最慢的一步长，或者另开一个线程按固定间隔续租。
- **同一会话串行，是在领任务的那条 SQL 里做的：** 这个会话已经有一个租约有效的任务在跑，就跳过它，先领别的。不用另外的锁。

## 21.3 告警风暴：排队，还是去撞上游的限流

值班场景有一种典型的高峰：一次故障，几十上百个人同时来问。跑 `examples/u21_backpressure.py`，这是一个离散事件模拟（程序按时间顺序推演每个请求何时发出、何时返回，不真的等待），不调模型，固定种子可复现：

- 100 个任务同时到达，每个任务顺序调 4 次模型，两次之间查一次工具（0.3 秒）。
- 模型服务同时只接 8 个请求，第 9 个直接返回 429。
- 单次调用的耗时取中位数 1.7 秒（接近单元十二实测的值）。
- 同一次调用最多重试 5 次，还失败，这个任务就算失败。
- 每种做法换 20 个随机种子，取平均。

| 做法 | 完成 | 发出的请求 | 其中 429 | 完成时间 p50 | p95 | 全部结束 |
|---|---|---|---|---|---|---|
| 不排队，429 了立刻重试 | 8 | 584 | 552 | 8.0 秒 | 8.6 秒 | 9.2 秒 |
| 不排队，指数退避重试 | 33 | 908 | 751 | 29.7 秒 | 38.7 秒 | 43.5 秒 |
| 排队，worker = 8（等于上限） | 100 | 400 | 0 | 54.3 秒 | 97.1 秒 | 102.7 秒 |
| 排队，worker = 16（上限的两倍） | 88 | 756 | 384 | 51.0 秒 | 86.5 秒 | 96.0 秒 |
| 排队，worker = 4（上限的一半） | 100 | 400 | 0 | 103.6 秒 | 190.8 秒 | 201.3 秒 |

完成时间只算完成了的任务。100 个任务都成功时，有用的请求是 400 个。

读这张表抓住三点：

- **重试解决不了过载。** 不排队时，立刻重试只做完 8 个；退避重试好一些，也只有 33 个，而且发出了 908 个请求，比全部做完需要的 400 个还多一倍多。上游已经满了，重试只会在它最忙的时候再加一份负载。
- **排队，并把 worker 数对齐上游，是唯一全部做完的做法。** 100 个全完成，400 个请求一个不浪费，一次 429 都没有。代价是排在后面的人要等：p95 是 97 秒。所以要告诉用户正在排队、前面还有几个（单元十二）；值班场景还可以合并：100 个人问的往往是同一个实例的同一次故障，按实例合并成一个任务，结果发给所有人。
- **worker 多了撞限流，少了浪费额度。** 16 个 worker 时有 384 次 429、12 个任务失败；4 个 worker 一次 429 都没有，可是慢了一倍。

模拟把上游的限额简化成了“同时几个请求”。真实的限额更细，Anthropic 的 API 文档写明了几条：

- 按每分钟请求数、每分钟输入 token、每分钟输出 token 分别限。
- 用令牌桶算法：额度按固定速度一点点补回来，所以一下子涌进来的请求即使没超过每分钟的总数，也可能被限流（文档的例子是每分钟 60 个，可能按每秒 1 个执行）。
- 从缓存读出的输入 token 不算进每分钟输入 token 的限额。
- 限流返回 429 时，通常带一个 retry-after，告诉你至少等几秒。
- 还有“爬坡限额”：用量每分钟最多比最近的峰值多涨一档，批量任务要从低处起步，均匀地发。

落到骨架上：

- 队列按 token 计量，不只按并发数；
- 网关遵守 retry-after；
- 批量任务从小并发开始，逐步放大。

## 21.4 配置：什么进指纹

骨架把配置分成两份：

| | 内容 | 进不进指纹 |
|---|---|---|
| 行为配置 | 模型、参数、系统提示词原文、工具定义原文、步数和 token 上限、打分器版本 | 进 |
| 运维配置 | worker 数、网关并发、重试次数、租约长度 | 不进 |

指纹是行为配置的哈希值，取前 12 位。实验里，给监控指标工具的描述末尾加一个句号，指纹就从 `f2a339b8fe0b` 变成了 `03e3c38a3e39`；把 worker 从 4 个改成 8 个，指纹不变。

为什么这么分：

- **会改变输出的，都要进。** 单元二看到，参数说明里的一个例子都会被模型照抄，工具描述改几个字，行为就可能变。用“v3”这样的标签管版本，迟早有人改了提示词忘了改标签；用原文算哈希，改了什么都会反映出来。
- **只影响快慢的，不进。** 加了几个 worker，评测结果不该变成“另一个版本”的。
- **每个任务、每条轨迹、每次评测都带上指纹。** 单元十七说，比较两个版本时除了要测的那一样，其他都要相同；单元十八说，榜单上的两个数字设置对齐了才能比。有了指纹，“设置是不是一样”就是比两个字符串。
- **指纹对应的完整配置存进数据库**（`configs` 表），两个指纹不一样时，能直接对比差在哪。
- **密钥不进配置**，从环境变量或密钥服务里读（单元十二）。

## 21.5 存储：一份事件日志，三处用

单元十二说过，事件日志既是恢复的依据，也是观测的数据源，还是评测的原材料。骨架里这三件事都从 `events` 表读：

- **恢复**（`runner.py`）：重放模型回复和工具结果，得到中断前的消息列表；最后一条模型回复里还没有结果的工具调用，补执行。
- **轨迹**（`trace.py`）：每条事件变成一个 span，见 21.6。
- **导出评测题**（`export.py`）：每个跑完的任务导出成一条候选：问题、当时每个工具的返回、Agent 的结论、配置指纹，正确答案留空等人标注。录下工具的返回，评测新版本时回放，每个版本看到的就是同样的数据（单元十四）。导出前脱敏，比如实验里慢查询日志的 `user_id = 1001` 变成了 `user_id = <ID>`。

几条做法：

- **只追加，不修改。** 写错了就追加一条更正，不去改旧的；这样日志本身就是审计记录。
- **执行的程序不存状态。** Anthropic 2026 年 4 月介绍 Claude Managed Agents 时说，会话是 harness 之外一份只追加的日志，harness 本身不存状态：挂了就新起一个，按会话 ID 读日志，从最后一个事件接着跑；要更多吞吐，就多起几个无状态的 harness。骨架里的 worker 就是这样，换哪个 worker 接手都一样。
- **框架把状态存在本地的，要镜像出去。** Claude Agent SDK 的部署文档说，会话记录默认写在本机磁盘上，重启、缩容、换机器都会丢；要用它提供的会话存储接口镜像到持久存储。镜像写入是尽力而为的，失败会发一条错误消息、丢掉这一批，文档建议对这类消息报警。
- **大的工具结果放对象存储**，事件里只存引用；日志设访问权限和保留期限（单元十二、十九）。

## 21.6 轨迹：用标准的名字，默认不带正文

从 C05 的事件日志生成的轨迹：

```
invoke_agent oncall  22.7 秒  会话 s-C05  任务 baf57dd0  配置 f2a339b8fe0b  第 2 次领取
     0.0s  start          {'config_id': 'f2a339b8fe0b', 'worker': 'w1'}
     2.4s  chat           输入   462  输出   86  2.4 秒
     2.4s  execute_tool   get_metrics      成功  131 字
     4.5s  chat           输入   620  输出   73  2.1 秒
     4.5s  execute_tool   query_slow_log   成功  241 字
    14.6s  resume         {'attempt': 2, 'worker': 'w4', 'after_seq': 4}
    17.3s  chat           输入   817  输出   98  2.7 秒
    17.3s  execute_tool   query_error_log  成功  374 字
    18.2s  chat           输入  1078  输出   22  1.0 秒
    18.2s  execute_tool   check_network    成功  52 字
    22.7s  chat           输入  1142  输出  168  4.4 秒
    22.7s  final          {'pred': 'SLOW_SQL', 'stop': 'done', 'turns': 5, 'tokens': 4566}
```

**名字用标准的。** OpenTelemetry 的生成式 AI 语义约定已经搬到了单独的仓库，截至 2026 年 11 月仍是 Development 状态。它规定了几种操作名：模型调用是 `chat`，工具执行是 `execute_tool`，一次 Agent 运行是 `invoke_agent`。它还区分了两种运行：控制流由模型通过工具调用决定的用 `invoke_agent`，由应用代码事先定好的用 `invoke_workflow`，正好对应单元三的 Agent 和 Workflow。

常用的属性有 `gen_ai.operation.name`、`gen_ai.provider.name`、`gen_ai.request.model`、`gen_ai.agent.name`、`gen_ai.conversation.id`。骨架再加上自己的几个：任务 ID、配置指纹、第几次领取，从一个指标能点到轨迹，再点到配置。

**正文默认不带。** 规范里，系统提示词、模型输出这类内容属性都要使用方主动打开，因为里面可能有个人信息。Claude Agent SDK 导出遥测时，提示词正文和工具输入默认也不导出。骨架的轨迹只记长度和成败；正文留在有权限控制的事件日志里，需要时按任务 ID 去查。轨迹往往要发到第三方的观测平台，事件日志不出你的系统。

## 做项目时

- 配置分成两份：会改变输出的（模型、参数、提示词原文、工具定义原文、上限、打分器版本）算指纹，只影响快慢的不进；每个任务、轨迹、评测结果都带上指纹。
- 事件日志只追加，作为唯一的记录：恢复、轨迹、导出评测题都从它读；执行的程序不存状态。
- 任务先进队列，用租约记录谁在跑；租约比最慢的一步长，每一步续租。
- 同一个会话串行，不同会话并行；在领任务时排除，不另加锁。
- worker 数按上游的限额定；真实的限额按请求数和 token 数分别算，队列按 token 计量，网关遵守 retry-after，批量任务逐步放量。
- 重试只在网关一处做；告警风暴时先排队、合并重复的问题，告诉用户在排第几。
- 轨迹用 OpenTelemetry 的名字，默认不带正文；正文留在有权限控制的日志里。
- 导出评测题时录下工具的返回、脱敏、标签留空等人标注。

## 面试常问

**一个生产级的 Agent 后端，你会怎么搭？**

几块：配置、存储、队列、网关、执行、轨迹。会改变输出的配置算一个指纹，跟着每个任务走；存储是一份只追加的事件日志加一张任务表；任务进队列，worker 用租约领任务，同一个会话串行；模型调用都经过网关，重试和并发上限只在那里做；执行的程序不存状态，从事件日志恢复。我用标准库写过一个几百行的骨架，跑 20 个排障任务时让一个 worker 中途崩溃，约 10 秒后另一个 worker 接手，从日志接着跑，没有重复查数据。

**上游模型限流了怎么办？重试够不够？**

不够。我模拟过 100 个任务同时到达、上游只接 8 个并发：不排队、429 了立刻重试，只做完 8 个；指数退避也只做完 33 个，还多发了一倍多的请求。排队、并把 worker 数对齐上游的限额，100 个全做完，一次 429 都没有，代价是后面的人要等，p95 约 97 秒。worker 开到 16 个，又会撞出 384 次 429。真实的限额按请求数、输入和输出 token 分别算，还有爬坡限额，所以队列要按 token 计量，网关遵守 retry-after，批量任务逐步放量。

**Agent 的轨迹要记什么？提示词和回复要不要进轨迹？**

一次运行一个 invoke_agent，下面挂每次 chat 和 execute_tool，记模型、token、耗时、工具名、成败，再加上任务 ID、配置指纹、第几次执行，名字用 OpenTelemetry 的生成式 AI 约定。提示词和回复的正文默认不进轨迹，规范里这类属性要主动打开，因为可能有个人信息；正文留在有权限控制的事件日志里，按任务 ID 去查。

## 自测

1. 骨架有哪几块？一个任务从提交到完成，经过哪几步？
2. 租约解决什么问题？租约设得太短会出什么事？
3. 实验里 C05 的 worker 崩溃以后发生了什么？为什么没有重复查数据？如果补执行的是有副作用的工具，要注意什么？
4. 同一个会话为什么要串行？骨架是怎么做到的？
5. 告警风暴的模拟里，不排队立刻重试、不排队退避重试、排队且 worker 等于上限，各做完多少任务、发出多少请求？为什么重试解决不了过载？
6. worker 数比上游的限额多一倍、少一半，各会怎样？真实的 API 限额和模拟有什么不同，队列和网关要怎么配合？
7. 哪些配置进指纹，哪些不进？为什么用原文算哈希，而不是“v3”这样的版本号？
8. 同一份事件日志用在哪三处？轨迹为什么默认不带正文？

## 延伸阅读

- Anthropic 文档，《Rate limits》：按请求数、输入 token、输出 token 分别限流，令牌桶算法，缓存读取不计入，retry-after，爬坡限额。
- Anthropic，《Scaling Managed Agents: Decoupling the brain from the hands》，2026 年 4 月：只追加的会话日志、无状态的 harness、按需创建的沙箱。
- Claude Agent SDK 文档，《Hosting the Agent SDK》：几种部署方式，本地会话记录的镜像，按内存估每台机器能跑几个会话。
- OpenTelemetry，生成式 AI 语义约定（semantic-conventions-genai 仓库）：invoke_agent、invoke_workflow、chat、execute_tool，内容属性默认关闭。
