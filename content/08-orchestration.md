# 单元八 编排和多 Agent

本单元的核心：多 Agent 不是更高级的 Agent，而是一种分工：买来并行和上下文隔离，代价是更多的调用，以及彼此看不到对方知道什么。先用一个 Agent；要拆，就把完整的上下文传下去，并让一个角色负责验收。

**学完这个单元，你能：**

- 说出几种多 Agent 编排方式各自谁掌握主导、适合什么场景。
- 用实测数据说明并行省了什么、没省什么，以及上下文不共享会怎样出错、怎么补救。
- 按一份公开的多 Agent 失败分类（MAST）检查一个设计，提前规避常见问题。

单元三列了几种 Workflow 形态，单元五测了子 Agent 省的是上下文峰值、不是钱。本单元把多 Agent 当成一个工程问题：怎么拆、怎么传上下文、怎么汇总、怎么验收、会怎么失败。先看几种编排方式，再用两组实验看并行和上下文共享，对照两个公开的大案例，然后讲验收、状态共享和典型失败。

## 8.1 几种编排方式

| 方式 | 谁掌握主导 | 适合 | 例子 |
|---|---|---|---|
| 单 Agent + 工具 | 一个循环 | 大多数任务，先从这里开始 | 单元三 |
| 主管-工作者（把 Agent 当工具） | 主 Agent 始终掌握回复，子 Agent 只交回结果 | 子任务边界清楚，最后要汇总 | 单元五的子 Agent、深度调研 |
| 交接（handoff） | 控制权转给专门的 Agent，由它接着和用户对话 | 先分诊，再由专门的 Agent 接手 | 客服：分诊 Agent 交给退款专员 Agent |
| 代码编排的并行 | 程序拆分、程序汇总，模型不参与编排 | 子任务固定、互相独立 | 4 台库各派一个子 Agent 排查 |
| 生成-评审 | 两个角色循环：一个产出，一个按标准检查 | 质量标准说得清楚 | 写好通报，再由评审检查是否一致 |
| 共享仓库 + 测试当裁判 | 没有主管，每个 Agent 自己挑任务、认领、提交 | 任务能拆成大量互相独立、能自动验证的小块 | 16 个 Agent 并行写 C 编译器（8.4） |
| 对等协作（群聊） | 多个 Agent 轮流发言 | 研究和演示居多，工程上难控制 | AutoGen、CAMEL |

“主管-工作者”和“交接”是最常被问到的一对。OpenAI 的 Agents SDK 把两者都做成了内置功能，区别在于**谁掌握回复**：把 Agent 当工具时，主 Agent 调用专家、拿回结果、自己继续回答；交接时，专家接过对话，后面由它直接回复用户。两者可以组合：分诊 Agent 交接给退款专员，退款专员再把“查物流”当工具交给另一个 Agent。

## 8.2 并行：省时间，不省钱

跑 `examples/u08_parallel.py`。4 台库各交给一个子 Agent 排查，拆分和汇总都由程序做。两种跑法各 3 遍：

| | 墙钟时间 | 每遍 token | 调模型次数 | 答对 |
|---|---|---|---|---|
| 顺序：一个跑完再跑下一个 | 29.4、31.7、24.6 秒（平均 28.6） | 9,680 | 12.0 | 4/4 ×3 |
| 并行：4 个同时跑 | 8.5、7.1、10.0 秒（平均 8.5） | 8,832 | 11.0 | 4/4 ×3 |

并行时，每一遍的墙钟时间正好等于这一遍里最慢的那个子 Agent。

读这张表抓住三点：

- **并行省的是时间。** 4 个互相独立的子任务同时跑，总耗时从约 29 秒降到约 9 秒。
- **不省钱。** 每个子 Agent 该调几次模型还是几次，两组的 token 差别只是随机波动。
- **总耗时由最慢的那个决定。** 一个子任务卡住，整体就卡住。所以每个子 Agent 都要有自己的轮数和时间上限，超时了用已有的结果先汇总。

并行还有一个前提：子任务真的互相独立。4 台库各查各的，满足；如果后一步要用前一步的结论，就只能顺序做。

## 8.3 上下文不共享，就会各说各的

多 Agent 最容易出的问题不是慢，而是**互相看不到对方知道什么**。Cognition 在《Don't Build Multi-Agents》里举过例子：让两个子 Agent 并行做一个游戏的两部分，一个做出了某种风格的背景，另一个做出了完全不搭的角色，因为各自都不知道对方的决定。

跑 `examples/u08_shared_context.py`。S4（user-mysql-04 写入全部失败）的故障通报分两部分：“根因分析”由带工具的排查 Agent 写（5 遍都查出了 DISK_FULL），“处置建议”由另一个 Agent 写。三种分工，各 5 遍：

| 分工 | 写建议的 Agent 看到什么 | 建议对准根因 |
|---|---|---|
| A 并行、不共享 | 只有用户的原话 | 0/5 |
| B 顺序、共享 | 用户原话 + 排查 Agent 的完整分析 | 5/5 |
| C 并行 + 评审 | 先按 A 写；评审检查“建议是否针对分析出的根因”，不一致就把分析交给它重写 | 5/5（评审退回了 5/5） |

A 组并不笨：“写入失败、读正常”本身就像磁盘满，5 遍的第一条建议都是查磁盘空间。但它不确定，于是把另外两条建议花在了别的可能性上：检查实例是不是被设成只读（4 遍）、查死锁和锁等待、查连接数耗尽。B 组拿到了分析，3 条建议全部围绕磁盘：清理 binlog、扩容数据盘、调整日志保留天数，还写出了具体命令。

关于这个“对准根因”的判定有一段插曲。第一版判定规则只检查“提到了磁盘处置，并且没提连接数、锁、慢查询、网络”，算出来 A 组是 3/5。逐条读原文发现规则有两个错：没把“检查是否只读”算作偏离，又把“清理慢查询日志文件”（其实是在腾磁盘）误判成了偏离。改正后 A 组是 0/5，和评审 Agent 的独立判断（5 遍全部退回，理由都是建议偏离了磁盘满这个根因）一致。打分规则本身也要拿原文逐条核对。

读这张表抓住三点：

- **拆分会切断上下文。** 写建议的 Agent 没看到证据，只能猜，而猜的时候会两头下注。在通报里，这种建议会让处理的人去查一堆不相关的东西。
- **最简单的修法是把上下文传下去。** B 组只是把分析原文交给了下一个 Agent。这也是 Cognition 那篇文章的原则：子任务要拿到完整的上下文，而不只是一句任务说明；能顺序做的就别并行。
- **评审能补救，但要付钱。** C 组的评审把 5 次都拦了下来，重写后全部对准。代价是每次多一次评审调用和一次重写，而且评审拿到了完整的分析，本质上还是“把上下文传过去”，只是传晚了。

## 8.4 两个公开的案例

前面两组实验规模都很小。Anthropic 公开过两个大得多的多 Agent 系统，正好落在两种编排方式上：

| | 多 Agent 调研系统（2025 年 6 月） | 并行写 C 编译器（2026 年 2 月） |
|---|---|---|
| 结构 | 主 Agent 拆分方向、派出子 Agent 并行搜索、汇总，最后由一个 Agent 核对引用 | 没有主管：16 个 Agent 各在一个容器里循环，每次自己挑下一项任务，用 git 仓库里的锁文件避免两个 Agent 做同一项 |
| 规模和花费 | token 约是普通对话的 15 倍（单个 Agent 约 4 倍） | 两周、近 2,000 个会话、约 2 万美元，写出约 10 万行、能编译 Linux 6.9 的 Rust 编译器 |
| 为什么有效 | 调研能拆成互相独立的方向。内部评测里，Opus 4 带 Sonnet 4 子 Agent 比单个 Opus 4 高 90.2%；BrowseComp（考联网查找难找事实的基准，单元十八）上，token 用量一项就解释了约 80% 的成绩差异 | 编译器测试能拆成大量互相独立的失败用例，每个 Agent 修一个；测试就是裁判 |
| 哪里卡住 | 主 Agent 同步等待：一个子 Agent 慢，全部等它；子 Agent 之间不能交流 | 编译 Linux 内核是一个整体任务，16 个 Agent 撞上同一个 bug、互相覆盖修改。改成拿 GCC 当参照：大部分文件交给 GCC 编，只把随机的一部分交给自己的编译器，才把问题拆开 |

读这张表抓住三点：

- **能拆成互相独立的子任务，并行才有用。** 两个案例成功的地方都天然可拆（调研方向、独立的失败测试），卡住的地方都拆不开（同步汇总、一个整体的内核）。投入也要按问题大小定：调研系统在提示词里写明，简单的事实查询 1 个 Agent、3 到 10 次工具调用，对比类问题 2 到 4 个子 Agent，复杂调研才派 10 个以上；早期版本会为简单问题派出 50 个。
- **交接要写清楚。** 调研系统早期给子 Agent 的任务说明太短，几个子 Agent 搜了同一件事；后来每个任务都写明目标、输出格式、用哪些工具和来源、边界在哪。子 Agent 把结果写进存储，只把引用交回主 Agent，避免层层转述丢信息。这和 8.3 的结论一致。
- **环境比提示词更要紧。** 编译器的作者说大部分精力花在环境上：测试要接近完美，否则 Agent 会去解决错的问题；加 CI，新提交不许弄坏已经通过的测试；测试输出只打几行、细节写进日志文件，避免占满上下文；提供一个只跑 1% 或 10% 抽样的快速模式，因为 Agent 感觉不到时间，会花几个小时跑全量测试。

## 8.5 评审和验收

“生成-评审”是最实用的多 Agent 形态：一个角色产出，另一个角色按标准检查，不合格就带着意见退回。8.3 的 C 组就是一个例子。用好它有几条要点：

- **评审要有明确的标准。** “建议是否针对分析出的根因”比“这份通报写得好不好”可检查得多。标准越具体，评审越稳定。
- **评审要看到被评的依据。** C 组的评审同时看到了分析和建议，才判断得出“不一致”。只看建议本身，它没法知道对不对。
- **能用程序检查的，就别用模型评审。** 单元四的证据核对、单元六的格式校验都是程序做的，确定、便宜、不会被说服。模型评审留给程序判断不了的东西：是否切题、是否一致、表达是否清楚。
- **退回要有次数上限。** 评审和生成可能来回拉锯；改两次还不过，就交给人。

Anthropic 2026 年 3 月的长任务 harness 把干活和评审分给两个 Agent，理由是模型给自己的成果打分普遍偏宽。几个做法值得借鉴：评审用浏览器真的把应用点一遍，而不是只读代码；每条标准有硬门槛，一条不过整轮不过；动手之前双方先约定“做完是什么样、怎么验证”。现成的模型当评审并不好用：它会发现问题，然后说服自己放过，作者是读评审日志、找出它和自己判断不一致的地方，反复改它的提示词才调好的。

代价也很直接：做一个复古游戏编辑器，单个 Agent 20 分钟、9 美元，做出来的游戏实体不响应输入；规划、生成、评审三个 Agent 跑了 6 小时、200 美元，才做出能玩的版本。作者的判断是，评审只在任务超出当前模型独立能稳定做好的范围时才值这个钱。

## 8.6 Agent 之间怎么共享状态

多个 Agent 协作，信息靠什么传？

| 方式 | 怎么做 | 注意 |
|---|---|---|
| 任务说明和结论 | 父 Agent 写一段任务说明交给子 Agent，子 Agent 交回一段结论 | 最常用，也最容易丢信息：说明写不全，子 Agent 就只能猜（8.3） |
| 共享的结构化状态 | 一个所有 Agent 都能读写的地方，比如证据账本、任务板 | 取证的子 Agent 把编号过的证据写进证据账本，主 Agent 从账本读，而不是从子 Agent 的散文里读 |
| 任务系统 | 每个任务存成一个文件或一条记录，有状态、依赖、负责人，Agent 认领执行 | learn-claude-code 的 s10、s13；能跨会话、能恢复。编译器案例更简单：认领就是往 git 仓库里提交一个锁文件 |
| 隔离的工作区 | 多个 Agent 改同一个代码仓库时，每个任务一个独立的工作目录（git worktree） | 否则会互相覆盖文件 |

原则是：**能结构化的就结构化。** 子 Agent 交回的结果最好是有固定字段的数据（发现、证据编号、出处、还缺什么），而不是一段散文，汇总时程序能检查、能合并（单元六）。

## 8.7 多 Agent 会怎么失败

UC Berkeley 的研究《Why Do Multi-Agent LLM Systems Fail?》（2025）分析了七个开源多 Agent 框架的运行记录，把失败归纳成 14 种、3 大类（MAST 分类）：

| 类别 | 典型失败 | 本书的对策 |
|---|---|---|
| 规格和系统设计 | 没按任务要求做；越出自己的角色；重复做同一步；丢了对话历史；不知道什么时候该结束 | 任务说明写清交付物和边界；每个 Agent 有轮数和预算上限；结束要经过完成检查（单元四的提交门） |
| Agent 之间不一致 | 对话被重置；不澄清就开干；偏离任务；该说的信息没说；忽略其他 Agent 的输入；嘴上说的和做的不一致 | 把完整上下文传下去（8.3）；结果用结构化数据交回（8.6）；能顺序做的不并行 |
| 任务验证 | 过早结束；没有验证或验证不完整；验证本身是错的 | 生成-评审（8.5）；能用程序验收的用程序；验收标准本身也要核对（8.3 的插曲） |

读这张表会发现，多 Agent 的失败大多不是“模型不够聪明”，而是系统设计的问题：任务没说清、信息没传到、结果没人验。这些问题在单 Agent 里也有，只是多 Agent 把它们放大了。

## 做项目时

- 先用一个 Agent 加好工具。只有需要并行（省时间）或隔离（单个上下文装不下）时才拆。
- 拆之前确认子任务互相独立；有依赖的顺序做，并把前一步的完整结果交给后一步。
- 每个子 Agent 有自己的轮数、预算和时间上限；最慢的那个决定总耗时。
- 子 Agent 交回结构化结果；需要共享的信息放进一个大家都能读写的结构化状态（账本、任务板）。
- 至少有一个角色负责最终验收：能用程序就用程序，判断不了的再用评审 Agent，评审要有具体标准、看得到依据、有退回次数上限。
- 多 Agent 的评测要看整体结果，也要看中间交接：信息有没有丢、有没有人越界、有没有人验收。

## 面试常问

**什么时候用多 Agent？有什么坑？**

它买来两样东西：并行省时间，上下文隔离让单个上下文更小。代价是调用更多，以及 Agent 之间看不到彼此知道什么。我实测过两件事。一是并行：4 台库各派一个子 Agent，顺序跑平均 29 秒，并行 9 秒，token 基本一样，并行省时间不省钱，总耗时由最慢的那个决定。二是上下文：把故障通报拆成根因分析和处置建议两个 Agent 并行写，写建议的那个看不到分析，5 遍都把一部分建议花在了查只读、查死锁这些无关方向上；改成顺序、把分析交给它，5 遍全部对准根因。所以先用单 Agent，要拆就把完整上下文传下去，并且有人负责验收。

**“把 Agent 当工具”和“交接”有什么区别？**

区别是谁掌握回复。把 Agent 当工具时，主 Agent 调用专家、拿回结果、自己接着回答用户，适合要汇总的场景；交接时控制权转给专家，由它直接和用户对话，适合分诊之后由专人接手，比如客服把退款问题交给退款专员。两者可以组合使用。

**多 Agent 系统一般怎么失败？**

UC Berkeley 的 MAST 分类把它归成三类：规格和系统设计问题（没按要求做、越界、重复、不知道何时结束），Agent 之间不一致（信息没传到、忽略别人的输入、偏离任务），任务验证问题（过早结束、没验证、验证错了）。对策都在工程上：任务说明写清交付物和边界，结果结构化交回，完整上下文传下去，有程序或评审负责验收，每个 Agent 有预算上限。
