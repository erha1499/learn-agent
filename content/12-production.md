# 单元十二 走向生产：状态、并发、网关、可观测、框架选型

本单元的核心：本地跑通一次和线上稳定跑一万次，差的是运行时工程：进程会崩，模型会慢、会断，用户会同时来，出了问题要查得到。Agent 特有的难处在于它既有副作用（建工单、发消息），又慢又贵：状态要能从事件日志恢复；有副作用的工具调用，要用业务身份而不是模型写的参数做幂等；模型调用要经过一个管超时、重试、并发、降级和计费的网关；每一轮都要留下能还原整条轨迹的记录。

**学完这个单元，你能：**

- 设计一个可恢复的 Agent 运行时：事件日志、重放、补执行，并用实验说明幂等键为什么要来自业务身份。
- 根据实测的延迟分布设定超时、重试和并发，说清模型网关要管哪些事。
- 设计 Agent 的可观测：一次运行一条轨迹、指标能点到轨迹；按几条标准选框架。

第二部分前几个单元讲的都是“让 Agent 做对”。本单元讲“让它在线上一直做对”。第四部分（单元二十到二十三）会讲通用的工程流程：立项、搭骨架、上线、上线以后；这里只讲 Agent 运行时特有的几件事。顺序是：先用实验看进程崩了怎么续（12.1），再讲并发和会话（12.2），用实验看模型调用的延迟、讲网关（12.3），然后讲可观测（12.4），最后讲框架怎么选（12.5）。

## 12.1 断了怎么续

一次排查要两分钟、二十多次调用（单元一 1.7），中途进程重启、机器迁移、发版，都会把它打断。最省事的办法是从头重跑，但 Agent 有副作用：已经建过的工单、已经发过的消息，重跑会再来一遍。

跑 `examples/u12_resume.py`。S1 场景里，Agent 查清根因后要调用 `create_ticket` 建一张工单，再回复用户。在工单建好之后、回复用户之前，进程“崩溃”。六种恢复方式，各跑 3 遍：

| 恢复方式 | 工单数 | 崩溃后又调模型 | 崩溃后又花 token |
|---|---|---|---|
| R1 从头重跑，工单系统不去重 | 2、2、2 | 4.3 次 | 4,844 |
| R2 从头重跑，按“工具名 + 参数”去重 | 2、2、2 | 5.0 次 | 6,013 |
| R3 从头重跑，按“任务 ID + 动作”去重 | 1、1、1 | 4.7 次 | 5,513 |
| R4 从事件日志恢复，崩在“执行完、已记账”之后 | 1、1、1 | 1.0 次 | 1,711 |
| R5 从事件日志恢复，崩在“执行完、还没记账”之间，不去重 | 2、2、2 | 1.0 次 | 1,654 |
| R6 同 R5，按“任务 ID + 动作”去重 | 1、1、1 | 1.0 次 | 1,564 |

R2 为什么没去重成功？3 遍里，模型两次写的工单标题都不一样，比如第一次是“order-mysql-01 连接数打满导致下单接口大量报错”，重跑时变成了“order-mysql-01 连接数打满问题”。参数是模型写的，每次都可能不同（单元一 1.4），用它做幂等键等于没做。

**事件日志**是这里的关键：每条消息、每次模型调用、每次工具执行，都按顺序追加一条记录。恢复时重放日志里的消息，得到崩溃前的 messages；如果最后一条模型回复里有工具调用还没有结果，就补执行，再接着循环。

读这张表抓住三点：

- **从日志恢复比重跑便宜得多。** 重跑要把查过的东西再查一遍，崩溃后又调了四五次模型；从日志恢复只需要一次调用，把回复写完。
- **幂等键要来自业务身份，不能来自模型写的参数。** “任务 ID + 动作”在重跑时不会变，按它去重才可靠（R3、R6）。
- **执行和记账之间总有一道缝。** R5 崩在工单已经建好、结果还没写进日志的那一刻：日志里看不出这一步做没做，只能补执行，于是建了两张。日志恢复和幂等要一起用，缺一个都不行。

oncall-agent-mvp 用的就是这一套：Claude Agent SDK 按会话 ID 恢复对话，自己再维护一份事件日志（JSONL），重启后重放日志重建程序状态（证据账本、阶段、预算），并给工具调用去重。LangGraph 的做法是每一步存一个检查点，它的文档同样要求把有副作用的操作做成幂等的。

## 12.2 并发和会话

一个线上 Agent 同时服务很多人，几条规则：

- **同一个会话串行，不同会话并行。** 同一个排查里，用户连发两条消息，不能让两个循环同时改同一份状态。oncall-agent-mvp 的会话调度是“1 主 + 5 副”的有界并发：同一话题的新消息按用户的操作分流（补充信息、纠正方向、提一个侧边问题），用快照隔离和 Redis 锁保证状态改动在锁内增量合并。
- **用户插话要有地方放。** Agent 跑着的时候用户又发了一句，可以排队等这一轮结束再处理，也可以在当前这批工具执行完之后插进去（pi 的“转向”和“追加”两个队列，单元四 4.6）。
- **并发有上限。** 模型服务按并发数或每分钟 token 数限流，数据库等下游也有承受能力。超过上限的任务进队列，前端告诉用户正在排队，而不是让所有请求一起超时。
- **长任务异步化。** 几分钟的任务不要占着一个 HTTP 请求：收到后放进任务队列，由后台的 worker 执行，结果通过消息推回去（单元二十一）。

## 12.3 模型网关

Agent 里每一次模型调用，都应该经过同一个网关。先看它要面对的延迟。跑 `examples/u12_latency.py`：同一个短请求（输出不超过 60 个 token）发 30 次：

| | 成功 | p50 | p90 | p95 | 最大 |
|---|---|---|---|---|---|
| 顺序发 30 次 | 30/30 | 1.63 秒 | 1.74 | 1.75 | 1.79 |
| 10 个并发，共 30 次 | 30/30 | 1.94 秒 | 2.04 | 2.05 | 2.05 |

顺序发 30 次合计 49.3 秒，10 个并发只用了 5.7 秒墙钟时间。

读这张表抓住三点：

- **这次的分布很集中，但别据此设超时。** 请求很短、输出固定在几十个 token 以内，延迟就很稳。真实的 Agent 调用输出长短不一，耗时几乎和输出长度成正比（单元一 1.3），一个要写五百字的调用要十几秒。超时要按“这一类调用的 p99”加余量来设，而不是按平均值。
- **并发提高了吞吐，也抬高了单次延迟。** 10 个并发时每次慢了约 0.3 秒，换来的是 30 次调用的总时间从 49 秒降到 6 秒。
- **失败不常见，但一定会来。** 这次 60 次全部成功；写这本书的过程中，就遇到过几次连接被服务端中途断开，示例客户端靠指数退避重试才跑完。

网关要管的事：

| 职责 | 做法 |
|---|---|
| 超时 | 按调用类型设：短的分类、抽取几秒，长的生成按预期输出长度算；流式调用另看首字时间 |
| 重试 | 只重试连接错误、限流（429）、服务端错误（5xx），指数退避加随机抖动，有次数上限。模型调用没有副作用，可以放心重试；工具调用不行（12.1） |
| 并发和限流 | 全局并发上限，按用户、按租户限额；超出排队 |
| 降级 | 主模型持续失败时切到备用模型，或者返回已有的部分结果、转人工 |
| 计费和预算 | 每次调用记下输入、输出、缓存命中的 token 和花费；每个任务、每个用户有预算，超了就停（单元三 3.4） |
| 缓存 | 前缀稳定时用显式缓存（单元六 6.4） |
| 密钥 | 统一保管和轮换，业务代码和 Agent 都拿不到真实的密钥 |

## 12.4 可观测

Agent 出了问题，第一个问题永远是“它这一次到底做了什么”。所以要做到：**一次运行一条轨迹，任何一个指标都能点进具体的轨迹。**

一条轨迹的结构：一次 Agent 运行下面挂着每一轮的模型调用和工具执行，每一步记下耗时、token、花费、输入输出（或者它们的摘要）、出错信息。12.1 的实验里，同一份事件日志就能直接还原成轨迹：

```
调模型    1.55 秒  输入   574  输出   46
执行工具 get_metrics
  结果入账：{"connections": 1000, "max_connections": ...
调模型    2.25 秒  输入   691  输出   78
执行工具 query_error_log
...
执行工具 create_ticket
  结果入账：已创建工单 INC-1001
调模型    4.27 秒  输入  1555  输出  165
```

**事件日志既是恢复的依据，也是观测的数据源，还是评测的原材料**（单元十三的轨迹就是它）。一份记录三处用，比三套记录各写各的可靠。

几条做法：

- **用标准的格式。** OpenTelemetry 为生成式 AI 定义了一套语义约定（模型调用、Agent 运行、工具执行各是什么样的 span，带哪些属性），截至写作时仍处在开发阶段。用它，就能接进现有的链路追踪系统。
- **记下版本。** 每条轨迹带上模型、提示词版本、工具版本、配置（单元六 6.5），否则出了问题没法复现。
- **指标从轨迹聚合出来。** 成功率、每例花费、耗时分布、每类工具的失败率，都是对轨迹做统计；发现异常时能一路点回具体的那几条（oncall-agent-mvp 的评测平台就是这样，单元十三 13.7）。
- **敏感信息要处理。** 输入输出里可能有用户数据和查询结果，存之前脱敏，设访问权限和保留期限。

## 12.5 框架怎么选

| 选项 | 是什么 | 适合 |
|---|---|---|
| 手写循环 | 单元三那十几行，加上你需要的机制 | 场景简单，或者想完全掌控每一步 |
| LangGraph | 用图描述流程，每一步存检查点，支持暂停等人工介入 | 流程有明确的阶段和分支，需要持久化和人工审批 |
| OpenAI Agents SDK | Agent、交接、护栏、会话、追踪几个基本概念 | 多 Agent 交接、以 OpenAI 模型为主 |
| Claude Agent SDK | Claude Code 的运行时做成的开发包：工具、hooks、子 Agent、技能、MCP、会话恢复 | 想直接用一个成熟的编程 Agent 级别的 harness |
| Google ADK | Google 的 Agent 开发包 | 以 Gemini 和 Google Cloud 为主 |
| pi | 极简的 harness，核心只有循环和几个工具，靠扩展加功能 | 想要小而可读的内核，自己决定加什么 |

选的时候问四个问题：

1. **四个位置能不能挂上自己的机制？** 组装上下文、执行前、执行后、想结束时（单元四 4.1）。权限、证据核对这些安全和验收的规则必须能挂上去。
2. **状态和恢复怎么做？** 有没有检查点或会话恢复，能不能和自己的事件日志配合（12.1）。
3. **能不能看到每一步？** 能不能拿到完整的轨迹，接进自己的观测系统（12.4）。
4. **绑定了什么？** 模型厂商、云平台、部署方式。换模型时要改多少。

oncall-agent-mvp 选了 Claude Agent SDK，接的是百炼的 Anthropic 兼容接口（qwen-plus），主要因为它开放了执行前后的 hooks，阶段规则、预算和证据核对都能挂上去；更早的手写循环版本保留在一个 git 标签里，两者的对比本身就是一个面试话题。

## 做项目时

- 每一步写事件日志：消息、模型调用、工具执行，带时间、token、版本。
- 恢复 = 重放日志 + 补执行没有结果的工具调用；有副作用的工具按“任务 ID + 动作”做幂等，和日志恢复一起用。
- 同一会话串行、不同会话并行；用户插话有队列；长任务进任务队列。
- 所有模型调用走一个网关：超时按 p99 加余量，只对可重试的错误重试，有并发上限、降级和预算。
- 一次运行一条轨迹，指标从轨迹聚合、能点回轨迹；敏感信息脱敏。
- 选框架看四点：能不能挂机制、怎么恢复、能不能看到每一步、绑定了什么。

## 面试常问

**Agent 跑到一半进程崩了怎么办？**

不能简单从头重跑，因为工具有副作用。我做过实验：Agent 建完工单、还没回复就崩溃，从头重跑 3 遍都建了两张工单；按参数去重也没用，因为重跑时模型写的工单标题每次都不一样。可靠的做法是两件事一起用：一是事件日志，每条消息、每次调用都追加记录，恢复时重放日志、补执行没有结果的调用，崩溃后只需再调一次模型，而重跑要四五次；二是有副作用的工具按“任务 ID + 动作”做幂等，因为执行和记账之间有一道缝，崩在那里时日志看不出做没做，只能补执行，没有幂等就会重复。

**模型网关要做哪些事？**

超时、重试、并发和限流、降级、计费和预算、缓存、密钥管理。超时按每类调用的 p99 加余量设，因为耗时几乎和输出长度成正比；我测过同一个短请求，顺序 30 次 p50 是 1.6 秒、最大 1.8 秒，10 并发时 p50 涨到 1.9 秒，但总时间从 49 秒降到 6 秒。重试只针对连接错误、429 和 5xx，指数退避加抖动；模型调用可以放心重试，工具调用要靠幂等。每个任务和用户有预算，超了就停。

**Agent 的可观测怎么做？**

一次运行一条轨迹，下面挂每一轮的模型调用和工具执行，记耗时、token、花费、输入输出摘要和版本；指标从轨迹聚合，能一路点回具体的轨迹。格式上可以用 OpenTelemetry 的生成式 AI 语义约定接进现有的链路追踪。我的做法是让事件日志同时做三件事：断点恢复的依据、观测的数据源、评测的轨迹，一份记录三处用。

**怎么选 Agent 框架？**

看四点：执行前后这些位置能不能挂自己的规则，状态怎么恢复，能不能拿到完整轨迹，绑定了哪家模型和平台。我的值班 Agent 用的是 Claude Agent SDK，因为它的 hooks 能挂阶段规则、预算和证据核对，接的是百炼的 Anthropic 兼容接口；更早有一个手写循环的版本，简单场景手写循环完全够用。

## 自测

1. 为什么 Agent 崩溃后不能简单从头重跑？实验里从头重跑和从日志恢复各花了多少？
2. 按“工具名 + 参数”做幂等键为什么失败了？幂等键应该来自哪里？
3. 什么是“执行和记账之间的缝”？为什么日志恢复和幂等要一起用？
4. 同一会话的消息为什么要串行？用户在 Agent 运行时插话，有哪几种处理方式？
5. 实验里顺序和并发的延迟分布各是怎样的？超时应该怎么设？为什么不能按这次的分布直接设？
6. 模型网关要管哪些事？为什么模型调用可以放心重试、工具调用不行？
7. 为什么说事件日志“一份记录三处用”？
8. 选 Agent 框架时问哪四个问题？
