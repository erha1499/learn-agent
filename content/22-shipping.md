# 单元二十二 上线：发布物、门禁、灰度、回滚

本单元的核心：Agent 的一次发布，改的不只是代码：提示词、工具描述、模型快照、接口版本，都会改变它的行为。所以发布物是钉死的配置指纹加模型快照，任何改变指纹的改动都走同一道门禁：底线必须守住，回归题不能做坏，和线上版本配对比较不能显著变差；单元二十的目标没达到，报出来，但不挡发布。上线先灰度，两个版本同时跑、先看过程指标；回滚就是把指针改回去，排队的改回旧版本，在跑的跑完自己的版本。

**学完这个单元，你能：**

- 说清一个 Agent 的发布物包含什么，为什么模型要写快照，为什么换模型和改提示词走同一道门。
- 实现一道发布门禁并解读它的结论：底线、回归题、配对比较、目标各起什么作用，没跑完的任务怎么处理。
- 设计灰度和回滚：怎么分流、先看什么指标、要多少个会话，回滚时在跑和排队的任务怎么办；说出几种部署形态。

单元二十一的骨架已经能跑、能恢复、能排队。上线要回答的是：怎么把一个改动安全地交给用户。单元十九列过发布的几道关（自动评测、影子、灰度、A/B），本单元把它们落到骨架上：先看六个改动过同一道门禁的结果，再讲发布物和模型版本、门禁的规则、灰度、回滚，最后是几种部署形态。

## 22.1 先看现象：六个改动，过同一道门

跑 `examples/u22_gate.py`。线上版本是单元十三的 Agent，模型写的是 qwen-plus。六个候选改动，都用骨架跑：线上版本和每个候选，在迷你评测集的 20 条用例上各跑 3 遍，由 `skeleton/gate.py` 判。

线上版本：答对 88%，答错 12%，每次 3,727 token，耗时 p90 16.4 秒，平均调工具 3.5 次。

| 改动 | 指纹 | 第一版规则 | 改过的规则 | 关键的数 |
|---|---|---|---|---|
| 运维：worker 4 个改成 8 个 | 不变 | 通过（不用跑） | 通过（不用跑） | |
| 提示词：证据不足说不知道 | 变了 | 不过 | 通过 | 答对 85%，答错 12%（和线上一样），转人工 3% |
| 提示词：最多查两个数据源 | 变了 | 不过 | 不过 | 答对 72%；做坏了 3 道回归题；答错率比线上高 16.7 ± 15.4 个点 |
| 模型：钉到 qwen-plus-2025-12-01 | 变了 | 不过 | 通过 | 答对 88%，和线上一样 |
| 模型：qwen-plus-2025-01-25 | 变了 | 不过 | 不过 | 答对 68%；7 个任务没跑完；做坏了 1 道回归题 |
| 模型：qwen3.7-plus | 变了 | 通过 | 通过 | 答对 100%；答错率比线上低 11.7 ± 10.9 个点 |

读这张表抓住四点：

- **换模型和改提示词一样，都是行为的变化。** 同一个系列早一年的快照，答对率掉到 68%；新一代的 qwen3.7-plus 默认开着思考，答对 100%，每次 3,078 token，耗时 p90 26.8 秒。不跑门禁，你不会知道换模型是升级还是降级。
- **我的第一版门禁规则错了。** 它把单元二十记分卡上的目标（答错率不超过 10%）当成了挡发布的门槛，可线上版本自己的答错率就是 12%。结果，和线上行为完全一样的“钉到快照”被挡下了，加一句“证据不足说不知道”也被挡下了。改过的规则把门槛分成两种：**底线**不管线上怎样都不能破，破了就不过；**目标**没达到只报出来，不挡发布，挡发布的是“比线上差”。这是本书又一次第一版规则写错。
- **没跑完的任务要单独看。** 老快照有 7 个任务报错退出，事后单独重跑同样的题，都能跑完；当时的错误原因没有记下来。门禁要把没跑完的任务和答错分开统计，记下原因，重跑以后再下结论，否则服务的一次抖动会被当成模型变差。去掉这 7 个，老快照的答对率也只有 77%，照样破底线。
- **耗时也会被当时的负载带偏。** 钉到快照和线上是同一个模型，耗时 p90 却从 16.4 秒到了 32.3 秒：门禁跑到这一组时，同一个账号下还有别的实验在并发调用。比耗时要同一时段跑（单元十七）。

## 22.2 发布物：钉死的配置，模型写快照

一次发布交出去的，是一组钉死的东西：

| 项 | 写成什么 | 为什么 |
|---|---|---|
| 代码 | 一个提交号、一个镜像 | 和普通服务一样 |
| 行为配置 | 配置指纹（单元二十一）：提示词原文、工具定义原文、参数、上限 | 改一个字行为就可能变 |
| 模型 | 快照的名字，不写会变的别名 | 别名背后的模型会换 |
| 评测集和打分器 | 版本号 | 分数要和同一套题、同一个打分器比（单元十四、十五） |
| 门禁结果 | 对哪个线上指纹、跑了几遍、结论 | 出了问题能查到当时凭什么放行 |

**模型写快照。** 本书一直用的 qwen-plus 是一个会变的名字。我对同一个请求分别调了 qwen-plus 和它的几个快照：qwen-plus、qwen-plus-latest、qwen-plus-2025-12-01 三个返回的 token 数完全一样，说明它们现在是同一个模型；qwen-plus-2025-01-25 只调了一个工具，行为明显不同。别名今天指向谁，明天可能就不是了。阿里云的文档里，qwen-plus 已经列在“旧版模型”下面。

Anthropic 的做法是从根上取消会动的别名：从 4.6 这一代起，每个模型 ID 本身就是一个钉死的快照，已有 ID 的权重和配置不再改，更新的版本用新的 ID 发布；更早的 4.5 系列还有会自动指向最新快照的短别名。它的文档也提醒：权重钉死了，路由、安全分类器、采样这些服务端的基础设施仍可能变，同一个 ID 出现意外的差异，最可能是基础设施的更新（单元十二讲过 2025 年 9 月那次复盘）。

**模型也会退役。** Anthropic 承诺在退役前至少提前 60 天通知，退役后的请求直接失败（返回 404）；文档建议在退役日期之前很早就测好替代的模型。比如 claude-sonnet-4-5-20250929 在 2026 年 9 月 30 日被标为弃用，计划 11 月 30 日退役，替代者是 claude-sonnet-5-5。接口本身也会变：在 2026 年 10 月 21 日的 API 版本里，temperature、top_p、top_k 这几个参数被去掉了，再传就返回 400。所以换模型、升接口版本都是发布，要走同一道门。

## 22.3 门禁怎么定

骨架里的门禁（`skeleton/gate.py`）按这个顺序判：

| 检查 | 规则 | 挡住什么 |
|---|---|---|
| 指纹 | 指纹没变（只改了运维参数），直接通过，不跑评测 | 不让无关的改动花钱、排队 |
| 底线 | 答对率不低于 80%，每次不超过 6,000 token，耗时 p90 不超过 60 秒；破了就不过 | 明显坏掉、成本或延迟失控的版本 |
| 回归题 | 线上版本每遍都做对的题，候选版本不能变成大多数时候做错（单元十三） | 修好一类、弄坏另一类 |
| 配对比较 | 每条用例上答错率的差，区间整个在 0 以上就不过；没显著但多错了 5 个点以上，多跑几遍再定（单元十七） | 整体悄悄变差 |
| 目标 | 单元二十记分卡上的门槛，没达到就报出来，不挡发布 | |
| 没跑完的任务 | 单独统计，记下原因；有就先查、重跑，再下结论 | 把服务的抖动当成模型变差 |

几条用法：

- **门禁放进 CI。** 每个改变指纹的提交都要过；线上版本的结果按指纹缓存，不用每次重跑。
- **门禁要花钱。** 一个候选 60 次运行，这里每次约 3,700 token，一次门禁二十几万 token；所以指纹没变就跳过，评测集分组（单元十四），日常提交跑回归集，发布前跑全量。
- **门禁看不见的，留给灰度。** 评测集只有 20 条，答错率多几个点的差距，门禁看不出来（配对区间都在 ±5 到 ±15 个点）。这就是为什么还要灰度。

## 22.4 灰度：两个版本同时跑，先看过程指标

灰度把一小部分新会话分给新版本，同时和旧版本比。它比单元十九的“变更前后比”好在一点：两个版本是同一时段、同一种流量，流量组成的变化、服务的抖动，对两边一样。

灰度能看出多大的变化，取决于每组有多少个会话。用 22.1 的线上数据算（80% 的把握，双侧 5%）：

| 要看出的变化 | 每组要多少个会话 |
|---|---|
| 答错率从 12% 变成 17% | 约 762 个 |
| 答错率从 12% 变成 22% | 约 217 个 |
| 答错率从 12% 变成 32% | 约 66 个 |
| 每次调工具从 3.5 次降到 1.9 次 | 约 5 个 |

读这张表抓住两点：

- **答错率几个点的变化，灰度很难看出来。** 线上也没有现成的对错标签（单元十九），要靠抽样核对，更慢。所以小的质量差距靠上线前的门禁挡，灰度挡的是大的、明显的变化。
- **过程指标几个会话就看得出来。** “最多查两个数据源”让每次调工具的次数从 3.5 降到 1.9，每组 5 个会话就够了。灰度的自动回滚条件，先用过程指标：工具报错率、每次调工具的次数、token、耗时、转人工的比例。

分几步放：先 1% 或内部员工，再 5%、25%、50%、100%，每一步有观察期，有自动回滚的条件。单元十二讲过 Anthropic 2026 年 4 月那次复盘后的改进：内部员工用和用户完全一样的版本，可能影响效果的改动要有观察期、跑更大的评测集、逐步放量。分流按会话 ID 的哈希（`skeleton/rollout.py`），同一个会话永远落在同一边。

## 22.5 回滚：改指针，在跑的跑完

骨架里，“线上用哪个版本”是数据库里的一个指针，发布和回滚都只是改这个指针（`store.deploy`），每次改动记一条发布记录。每个任务在提交时就钉在当时的版本上，之后不管指针怎么变，它都按自己的版本跑完。

跑 `examples/u22_rollout.py`：v1 是线上版本，v2 是那个“最多查两个数据源”的改动。

| 时间 | 发生了什么 |
|---|---|
| 0 秒 | 上线 v1；8 个会话全走 v1 |
| 14.7 秒 | 打开灰度：新会话按会话 ID 的哈希，一半走 v2；又进来 16 个会话 |
| 45.6 秒 | v2 做完 6 个会话后检查：v2 平均调工具 1.7 次、答错 3 个；同期的 v1 是 3.8 次、答错 0 个。回滚 |
| 之后 | 8 个新会话全走 v1 |

6 个会话就看出了差别，正好印证 22.4：过程指标几个会话就够。回滚那一刻，v2 的任务有 6 个已完成、1 个正在跑、1 个在排队。排队的那个改回了 v1（`repin_queued`）；正在跑的那个按 v2 跑完。

几条做法：

- **同一个会话从头到尾用一个版本。** 一个 Agent 任务要跑几分钟，中途换版本，前半段的提示词和后半段的工具定义可能对不上。按会话钉版本，灰度分流也按会话哈希，同一个用户不会这次 v1、下次 v2 来回跳。单元十二提过，Anthropic 的调研系统发版时也是新旧版本并存、流量逐步切换。
- **排队的改回去，在跑的看情况。** 还没开始的任务改回稳定版本没有任何代价；在跑的任务，可以让它跑完，也可以中止后转人工，看坏版本错一次的代价（单元二十）。
- **动作回滚不了。** 指针能改回去，已经发出去的消息、已经重启的实例改不回来。这正是单元二十说权限先窄后宽的原因：灰度期间，新版本最好只读加建议。

## 22.6 部署形态

Claude Agent SDK 的部署文档总结了几种形态：

| 形态 | 做法 | 适合 |
|---|---|---|
| 一次性 | 每个任务起一个容器，做完就销毁 | 修一个 bug、处理一份文件这类独立任务 |
| 长驻 | 常驻的容器里跑很多会话，前面是 HTTP 或 WebSocket | 需要随时响应的对话 |
| 混合 | 一次性的容器，启动时从会话存储里恢复，结束时写回去 | 两次交互之间会空闲很久的会话 |

几个数：文档给的起步配置是每个 Agent 1 GiB 内存、5 GiB 磁盘、1 个 CPU，内存随会话变长、工具用得多而增长；一台机器能跑几个会话主要由内存决定，按“（机器内存 − 开销）÷ 每个会话的内存上限”估，峰值要实测。花费的大头不在机器：文档说 token 的花费比容器高一个数量级以上，一个最小的容器大约每小时 0.05 美元。

和安全有关的几条（单元十一）：每个会话跑在隔离的容器里；出网走代理，按租户设规则；模型的密钥从密钥服务读，工具要用的凭据放在出网代理里，不放进 Agent 能看到的环境；多租户时每个租户各用一套配置目录和工作目录。

## 做项目时

- 发布物是一组钉死的东西：代码版本、配置指纹、模型快照、评测集和打分器的版本、门禁的结论。
- 模型写快照，不写会变的别名；换模型、升接口版本，和改提示词一样走门禁。盯着模型的弃用通知，在退役之前很早就测好替代者。
- 门禁分清底线和目标：底线和“不比线上差”挡发布，目标只报出来。
- 门禁里没跑完的任务单独统计、记下原因、重跑，不当成答错。
- 指纹没变就跳过评测；线上版本的结果按指纹缓存；日常跑回归集，发布前跑全量。
- 灰度按会话哈希分流，两个版本同时比；自动回滚先看过程指标；小的质量差距靠门禁挡。
- 回滚就是改指针：排队的改回旧版本，在跑的跑完或者中止转人工；灰度期间新版本最好只读加建议。
- 部署形态按任务选；按内存估每台机器的会话数；密钥和凭据不进 Agent 能看到的环境。

## 面试常问

**Agent 的版本怎么管？换模型怎么上线？**

发布物是钉死的一组东西：代码版本，加上配置指纹（提示词原文、工具定义原文、参数、上限算一个哈希），加上模型的快照名，再加上评测集和打分器的版本。模型不写会变的别名：我实测过，qwen-plus 这个名字现在和 2025-12-01 的快照完全一样，可同一系列早一年的快照答对率只有 68%。换模型和改提示词一样走门禁；Anthropic 从 4.6 这一代起，每个模型 ID 本身就是钉死的快照，退役前至少提前 60 天通知，要在那之前测好替代者。

**发布门禁怎么设计？**

指纹没变就跳过；变了就在评测集上跑几遍，和线上版本比。挡发布的有三类：底线（答对率、token、耗时有一条不管线上怎样都不能破的线）、回归题（线上每遍都对的题不能做坏）、配对比较（答错率显著变差）。记分卡上的目标没达到只报出来。我第一版把目标当成了门槛，可线上版本自己都达不到，连行为完全不变的改动都过不去。另外，没跑完的任务要单独统计、查原因、重跑，不能当成答错。

**灰度和回滚怎么做？**

按会话 ID 的哈希把一小部分新会话分给新版本，两个版本同时比，先看过程指标：我算过，答错率从 12% 涨到 22%，每组要两百多个会话才看得出；可每次调工具的次数从 3.5 降到 1.9，每组 5 个会话就够。回滚是把线上指针改回去：每个任务在提交时就钉在当时的版本上，排队中的改回旧版本，正在跑的按自己的版本跑完。已经执行的动作回滚不了，所以灰度期间新版本最好只读加建议。

## 自测

1. 一个 Agent 的发布物包含哪些东西？为什么模型要写快照，不写别名？
2. 六个改动过门禁，各是什么结论？换模型和改提示词，结果说明了什么？
3. 第一版门禁规则错在哪？底线和目标有什么区别？
4. 门禁里没跑完的任务为什么要单独统计？耗时为什么也会被带偏？
5. 门禁的几类检查各挡住什么？门禁的花费怎么控制？
6. 灰度为什么比“变更前后比”可靠？答错率的变化和过程指标的变化，各要多少个会话才看得出？
7. 回滚时，正在跑的任务和排队中的任务各怎么处理？为什么说动作回滚不了？
8. Agent 有哪几种部署形态？一台机器能跑几个会话，怎么估？
