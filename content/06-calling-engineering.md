# 单元六 调用工程：结构化输出和提示词

本单元的核心：一次模型调用要变成程序能依赖的零件，靠三件事。输出交给程序之前一定过校验，能由接口约束的格式就别只靠提示词请求；提示词当代码管：结构清楚、不变的放前面、例子慎用、改了要评测；用缓存把每轮重复的部分变便宜，而缓存是否生效取决于你怎么排提示词。

**学完这个单元，你能：**

- 比较四种拿结构化输出的做法，说出每种保证什么、不保证什么，以及为什么校验永远不能省。
- 写出结构清楚、对缓存友好的提示词，知道规则、例子、格式说明、当前状态各放在哪。
- 用实测数据解释隐式缓存和显式缓存的区别，估算缓存能省多少。

第二部分从这里开始，默认你读过第一部分，或者已经用框架搭过 Agent。第一部分留下了几个关于“一次调用”的问题：模型说只输出 JSON，结果把括号写错了；参数说明里的一个例子被照抄了 10 次；缓存要求“不变的放前面”，但还没验证过写法到底有多大影响。本单元先讲结构化输出和校验，再讲提示词怎么写、缓存怎么命中，最后讲提示词怎么管。

## 6.1 四种拿结构化输出的做法

任务：把值班群里的一条消息整理成工单 JSON，字段是实例名、严重程度（P0、P1、P2 三选一）、现象、开始时间（HH:MM）。4 条消息里，一条没提实例名，一条没提时间，提示词要求没提到的填 `null`。跑 `examples/u06_structured.py`，四种做法，每条消息各 5 遍，共 20 次：

| 做法 | 怎么做 | 合法 JSON | 符合格式 | 严重程度对 | 实例名对 | 时间对 |
|---|---|---|---|---|---|---|
| A 只靠提示词 | “只输出 JSON，字段如下……” | 20/20 | 20/20 | 20/20 | 20/20 | 20/20 |
| B JSON 模式 | `response_format={"type": "json_object"}` | 20/20 | 20/20 | 20/20 | 20/20 | 20/20 |
| C JSON Schema 严格模式 | `response_format` 里给 schema，`strict: true` | 20/20 | 15/20 | 20/20 | 20/20 | 15/20 |
| D 强制工具调用 | schema 写成一个工具的参数，`tool_choice` 指定必须调它 | 20/20 | 20/20 | 20/20 | 20/20 | 20/20 |

C 的 5 次不合格，全是同一条消息（“大概 9 点半开始的”）：开始时间写成了 `9:30`，不是要求的 `09:30`。schema 里只在描述里写了“格式 HH:MM”，没有用 `pattern` 约束，严格模式就不管它。

还有一次试跑的观察：用 JSON 模式、但提示词里没列出严重程度的可选值时，模型返回了 `"severity": "critical"`。JSON 是合法的，值不在你的程序认识的范围里。

读这张表抓住三点：

- **短而简单的 JSON，四种做法这次都几乎不出错。** 但单元一那次更长的输出就把括号写错了。一天调用几十万次时，千分之一的格式错误就是几百次故障。接口层面的约束（JSON 模式、严格模式、强制工具调用）把“大概率对”变成“结构上一定对”，量大时值得用。
- **各种约束保证的东西不一样。** JSON 模式只保证是合法 JSON，不管字段和值；严格模式保证字段、类型、枚举值，不保证没写进 schema 的格式和含义；强制工具调用和严格模式类似，还能顺便复用工具调用的那套代码（单元二）。没有哪一种保证“值是对的”。
- **校验永远不能省。** C 那 5 次格式不对，只有程序校验发现了。值对不对（实例名是不是编的、时间是不是消息里说的），更是只能靠程序和评测。

| 做法 | 保证什么 | 不保证什么 |
|---|---|---|
| 只靠提示词 | 什么都不保证，靠模型配合 | 一切 |
| JSON 模式 | 合法 JSON | 字段、类型、取值 |
| JSON Schema 严格模式 | 字段、类型、枚举、必填 | schema 外的格式要求、值的正确性 |
| 强制工具调用 | 和严格模式相近（取决于服务商是否严格校验参数） | 值的正确性 |

各家接口对这些功能的支持不一样（是否支持严格模式、支持哪些 schema 关键字），以文档为准。

## 6.2 校验和重试放在哪

程序拿到模型的输出，按顺序做三层检查：

1. **能不能解析**：`finish_reason` 是不是 `stop`（不是被截断），JSON 能不能解析。
2. **格式对不对**：字段、类型、枚举、格式（时间、编号）是否符合 schema。
3. **值合不合理**：实例名是不是用户说过的，引用的证据编号是不是存在（单元四的参数守卫和提交门），数值在不在合理范围。

不合格时，最常用的处理是**把具体问题发回去，让模型改一次**：“你的输出有问题：started_at='9:30' 不是 HH:MM，请只输出修正后的 JSON”。实验里的 A+ 就是这样做的，这次 A 没有出错，重试没有被触发。重试要有次数上限，改不好就走兜底：返回默认值、转人工、或者让上层知道这一步失败了。

两个常见的坑：

- **schema 要给“不知道”留位置。** 实验里实例名的类型是“字符串或 null”，没提到的就填 null，4 条消息全对。如果 schema 要求实例名必须是字符串，模型就只能编一个，这和单元二编参数是同一个问题，只是换了个地方。
- **能用程序做的格式化，别让模型做。** 时间写 `9:30` 还是 `09:30`，交给程序规整一下比让模型反复改便宜得多。让模型做它擅长的“理解”，把“格式”留给代码。

## 6.3 提示词怎么写

提示词是模型每一轮看到的说明书。几条经过前面单元实验检验的原则：

**分块写，每块一件事。** 一个 Agent 的系统提示词通常有这几块，用标题或标签隔开：

| 块 | 写什么 | 例子 |
|---|---|---|
| 身份和任务 | 你是谁、要完成什么、交付什么 | “你是数据库值班助手，查清根因后提交结论” |
| 规则 | 硬规则和偏好分开；写清理由，模型更能举一反三 | “结论必须引用证据编号，因为结论会直接发给业务方” |
| 工具和格式 | 什么时候用哪个工具、输出格式 | 大部分写在工具描述里 |
| 例子 | 少量、多样、标明是例子 | 见下文 |
| 当前状态 | 本轮会变的信息 | 放在最后 |

**例子会被照抄。** 单元二里，参数说明里写了“例如 order-mysql-01”，用户没给实例名时，模型 10 次都填了这个例子。例子最擅长教格式和风格；给例子时要多样，覆盖不同情况，并明确说“以下只是格式示例”，涉及具体值的地方用明显的占位符。

**说“要做什么”，也说“做不到时怎么办”。** 单元三里，提示词要求根因五选一，工具全挂时模型 5 遍编了 4 种根因；加一句“查不到证据就写 UNKNOWN 并说明还缺什么”，5 遍都如实说了。很多“幻觉”其实是提示词没给合法的出路。

**提示词只能提高概率。** 必须成立的事（权限、证据、格式）交给程序。提示词里写了“不要编造”，模型照样会编。

**长度看相关性，不看长短。** pi 的系统提示词很短，Claude Code 的很长，两者都好用。要避免的是“每轮都发、但大多数时候用不上”的内容：这类内容做成技能，按需加载。

## 6.4 缓存：前缀不变才省钱

原理在单元一讲过：两次调用的输入开头完全相同，后一次可以复用算好的部分，服务商按折扣收费。百炼有两种缓存（2026-11 文档，以官方为准）：

| | 怎么开 | 命中怎么收费 | 特点 |
|---|---|---|---|
| 隐式缓存 | 系统自动识别公共前缀，不用做任何事 | 输入单价的 20% | 不保证命中 |
| 显式缓存 | 在消息上标 `cache_control` | 创建时按 125%，命中按 10% | 5 分钟内确定命中，每次命中重新计时 |

跑 `examples/u06_cache.py`。模拟一个 Agent 跑 6 轮：系统提示词约三千 token（规则加 5 份排查手册），每轮在末尾追加一段工具结果，每次只让模型输出几个字。三种写法，各跑 2 次：

| 写法 | 6 轮里命中几轮 | 命中率 | 6 轮输入花费（不缓存是 ¥0.0152） |
|---|---|---|---|
| A 前缀不变，当前状态放在最后（隐式缓存） | 2～3 轮 | 31%、47% | ¥0.0115、¥0.0095 |
| B 每轮在系统提示词开头插入当前时间和状态（隐式缓存） | 0 轮 | 0% | ¥0.0152 |
| C 前缀不变 + 显式缓存 | 第 2 轮起每轮 | 78% | ¥0.0052 |

读这张表抓住三点：

- **会变的东西放在开头，缓存就全废了。** B 两次都是 0%：第一行变了，后面三千 token 一个都对不上。“当前时间”“剩余预算”这类每轮都变的信息，要放在输入的最后。
- **隐式缓存省一些，但不稳定。** A 的前缀完全不变，6 轮里也只命中了两三轮，说明“不保证命中”是真的，估算成本时不能按 100% 命中算。
- **显式缓存把“可能”变成“确定”。** C 从第 2 轮起每轮都命中，即使加上创建时多收的四分之一，输入花费也只有不缓存的三分之一左右。Agent 每轮重发同一段系统提示词和工具定义，正是显式缓存最适合的场景。Anthropic 的接口也是类似的显式缓存机制。

这也给了一个排查方法。线上的缓存命中率突然下降时，先打印两次相邻调用的完整输入，找出第一个不同的字：会变的内容出现在哪里，它后面的部分就都命中不了。插在系统提示词里或者历史的前面，就会打断；只追加在每轮的最后，就不影响前面已有的部分。

## 6.5 提示词也是代码

提示词改一个字，行为就可能变（单元二、单元三的实验都是一句话的差别）。所以它要像代码一样管：

- **放进版本控制，和代码一起评审。** 一种做法是把所有提示词放在一个文件里，按版本开关拼装，每个版本都有名字。
- **每次运行都记下用的是哪个版本。** 评测和线上的每条轨迹都带着提示词版本和模型版本，出了问题才能回溯。
- **改了就跑评测。** 在同一批用例上和旧版本比，多跑几遍，看配对的差别。只在几个例子上试一下“感觉更好了”，是最常见的退步来源。
- **换模型就重新调。** 同一份提示词在不同模型上效果不同，换模型要把评测重跑一遍。

## 做项目时

- 交给程序的输出一律校验三层：能解析、格式对、值合理。不合格就带着具体问题重试一次，有上限，再不行走兜底。
- 量大的调用用接口层的约束（严格模式或强制工具调用）；schema 给“不知道”留位置，能用 `pattern`、`enum` 约束的就写进去。
- 能由程序做的格式化，不交给模型。
- 提示词分块写：身份任务、规则（带理由）、工具和格式、例子、当前状态；例子多样并标明是示例；给“做不到时怎么办”留出路。
- 会变的内容放在输入最后；每轮重复的系统提示词和工具定义用显式缓存；定期看缓存命中率。
- 提示词进版本控制，改了就在评测集上和旧版比。

## 面试常问

**怎么保证模型输出的 JSON 能用？**

分两层。生成时尽量用接口的约束：JSON 模式只保证合法 JSON，严格模式和强制工具调用能保证字段、类型、枚举。生成后一定用程序校验三层：能解析、格式对、值合理，不合格就把具体问题发回去重试一次，再不行走兜底。我实测过，短 JSON 四种做法基本都不出错，但严格模式也有 5 次把时间写成 9:30 而不是 09:30，因为格式只写在描述里，schema 没约束，最后是程序校验发现的。还有 schema 要给“不知道”留位置，必填的字符串会逼模型编一个。

**提示词缓存是怎么回事？怎么设计提示词才能命中？**

两次调用的输入开头完全相同时，服务端可以复用算好的中间结果，按折扣收费。所以不变的内容（系统提示词、工具定义）放前面，会变的（当前时间、状态）放最后。我实测一个六轮的 Agent：把当前状态插在系统提示词开头，命中率是 0；前缀不变时隐式缓存命中 31% 到 47%，不稳定；加上显式缓存后从第二轮起每轮都命中，输入花费降到三分之一左右。Agent 每轮重发同样的系统提示词和工具定义，最适合显式缓存。

**提示词怎么管理？**

当代码管：进版本控制、和代码一起评审；每次运行记下提示词和模型的版本；改了就在评测集上和旧版本做配对比较，多跑几遍；换模型要重新评测。一句话的改动就能让行为变化很大，比如我在参数说明里加一句“不知道就先问用户”，编参数从 10 次降到 1 次。

## 自测

1. JSON 模式、JSON Schema 严格模式、强制工具调用，分别保证什么、不保证什么？
2. 实验里严格模式为什么会输出 `9:30`？怎么改才能避免？
3. 程序拿到模型的结构化输出，要检查哪三层？不合格时怎么处理？
4. 为什么说“schema 要给不知道留位置”？和单元二的编参数有什么关系？
5. 提示词里的例子有什么风险？怎么给例子更安全？
6. 隐式缓存和显式缓存有什么区别？实验里“在开头插入当前状态”为什么命中率是 0？
