# 单元九 上下文工程和记忆

本单元的核心：上下文是一张有限又昂贵的工作台，每一轮都要整张重发。上下文工程就是决定每一轮放什么：工具输出先压缩，长会话按字段结构化地压缩而不是截断，跨会话要记的写进记忆。

**学完这个单元，你能：**

- 说出一轮输入由哪几部分组成，量出谁占大头。
- 比较截断、朴素摘要、结构化摘要几种压缩策略的效果和成本，写出一个好的压缩提示词。
- 设计一个跨会话的记忆：存什么、不存什么、怎么召回、怎么处理过期。

前面几个单元从不同角度碰到过上下文：Agent 每一轮都要重发前面的全部内容；刷屏的日志可以在源头压缩；子 Agent 能隔离上下文，技能能按需加载；缓存要求不变的放前面。本单元把它们收拢成一个问题：一个长会话里，每一轮的输入该放什么。先量一轮输入的构成，再用实验比较几种压缩策略，然后讲跨会话的记忆，最后给一张清单。

## 9.1 一轮输入里都有什么

`examples/u09_long_session.py` 模拟了一段排查对话：用户在前几轮陆续交代了 6 个关键事实（实例、开始时间、“主库不能重启”、网络已排除、14:00 刚扩容到 40 个实例、结论同步到 #db-oncall 群），中间夹着 8 段很长的工具输出（错误日志、会话列表、pod 列表、配置）。最后用户说：“我要下班了，写一段交接给下一班。”

用单元一的办法单独量每一部分的 token，最后一轮的输入是这样构成的：

| 部分 | token | 占比 |
|---|---|---|
| 系统提示词 | 14 | 0% |
| 用户说的话（6 个关键事实都在这里） | 119 | 0% |
| 助手回复和工具输出 | 89,113 | 100% |

真正重要的信息只占一百多个 token，剩下八万九千个几乎全是工具的原始输出。这和单元一看到的一样：输入的大头是历史里的工具结果，每一轮都要整张重发。所以上下文工程的第一刀，永远砍在工具输出上。

## 9.2 长会话压缩：四种策略

上下文快满时，最后一轮之前的历史有四种处理方式。同一段对话，每种跑 3 遍，看交接里写对了几个事实：

| 策略 | 怎么做 | 写对的事实（共 6 个） | 最后一次调用的输入 | 压缩本身多花 |
|---|---|---|---|---|
| A 完整历史 | 什么都不删 | 6、6、6 | 89,317 token | 0 |
| B 截断 | 只留最近 6 条消息 | 2、2、3 | 49,904 token | 0 |
| C 朴素摘要 | 更早的部分让模型“总结一下以上对话”，用摘要代替原文 | 6、5、5 | 51,355 token | 约 40,900 token |
| D 结构化摘要 | 同样压缩，但指定要保留的字段：事实、约束、已排除、变更、待办；不保留原始日志 | 6、6、6 | 51,137 token | 约 40,700 token |

摘要本身保住了几个事实：朴素摘要是 5、4、5，漏掉过“已排除网络”和“同步到哪”；结构化摘要是 5、5、5，只漏了“同步到哪”，而这一条恰好在保留的最近 6 条里，所以最后的交接是全对的。

有两个现象比数字更值得记住：

- **截断以后，模型会编。** B 组 3 遍的交接里，“实例”一栏都写成了 order-service 而不是 order-mysql-01；3 遍都编出了一次“今日 13:30（或 13:58）上线 order-service v2.4.7”，其中两遍还建议下一班回滚这个版本；还有两遍写了“TCP 重传率 < 0.01%”。这些事在对话里根本没有出现过。交接模板要求填这些栏，原文又被删掉了，它就按“最像的样子”填上了。这是单元一说过的幻觉，起因是上下文管理，而下一班照着做，就会去回滚一个不存在的版本。
- **完整历史也会“做”没发生的事。** A 组 3 遍都写了“结论已同步至 #db-oncall 群”，可是没有任何人、任何工具发过这条消息。用户说的是“结论出来后同步”，模型把待办写成了已办。所以 Agent 声称做了的动作，要以工具调用记录为准。

关于判定还有一段插曲。第一版检查“约束”的规则只认“不能、不要、禁止”这几种说法，算出来 A 组 3 遍都漏了约束；读原文才发现模型写的是“严禁重启”“不可重启”“不重启”。改正规则后 A 组是 6、6、6。和单元八一样：打分规则要拿原文逐条核对。

读这张表抓住三点：

- **截断最便宜，也最危险。** 它丢的是最早的那几轮，而用户交代背景、提出约束，恰恰都在最早的那几轮。丢了还不会报错，模型会编一个填上。
- **摘要要写清“保留什么”。** 朴素的“总结一下”会按模型自己觉得重要的来写，大段复述日志里的数字，漏掉“已排除”这类结论。结构化的压缩提示词列出必须保留的字段，并明确“不要原始日志，只要从日志里得出的结论”。
- **压缩本身要付钱，而且这次没省下多少。** 写摘要要把旧的那部分读一遍（约 4 万 token）；压缩后最后一次调用仍有 5 万 token，因为保留的“最近 6 条”里有几段大日志。按条数保留是个粗糙的做法，应该按 token 数保留，并且先压缩工具输出，再压缩历史。

完整历史这次全对，因为 8.9 万 token 还在 qwen-plus 的上下文窗口里，而且只问了一次。如果会话继续，每一轮都要再付 9 万 token，会话越长越接近窗口上限，中间的信息也越容易被忽略。压缩的目的是让会话能便宜地继续下去，而不是让这一次回答更准。

## 9.3 什么时候压，怎么压

**什么时候压。** 不要等到报错。pi 的做法是在输入超过“上下文窗口减去一段预留”时压缩，预留是给回答留的位置；learn-claude-code 按大小分了几级，先做不花模型调用的整理，最后才写摘要。

**三种工具，管三种增长。** Anthropic 的接口把上下文管理拆成三样（2026 年 3 月的官方示例）：

| 工具 | 做什么 | 适合 | 代价 |
|---|---|---|---|
| 清除旧工具结果 | 把较早的工具结果换成一个占位符，保留“调用过这个工具”的记录 | 工具结果大，需要时可以再查一次 | 被清掉的要重新调工具；每清一次，输入的前缀就变了，缓存要重建 |
| 压缩 | 把整段历史写成摘要 | 来回很多轮的长对话 | 有损：摘要提示词决定留下什么，细节最容易丢 |
| 记忆工具 | 模型自己在一个文件目录里读写笔记，会话结束也还在 | 要跨会话保留的东西 | 记什么全靠模型判断 |

《Effective context engineering》把清除旧工具结果称作最安全、最轻的一种压缩：一个工具结果在历史里埋得很深以后，很少还需要原文。三样可以叠着用，但要把记忆工具排除在清除之外，否则记忆的读写也会被清掉。

**按什么顺序压。** 从便宜、不丢信息的开始：

1. 工具输出在进入上下文之前就合并、截断。
2. 旧的大段工具结果存到文件里，上下文只留路径和一行说明，需要时还能读回来。
3. 最后才让模型把更早的历史写成摘要，保留最近一段原文。保留多少按 token 算，不按条数算。

**压缩提示词怎么写。** 参照 9.2 的 D 组，列出必须保留的字段：

| 字段 | 例子 |
|---|---|
| 目标和当前状态 | 排查 order-mysql-01 下单失败，已定位到连接数打满 |
| 用户给出的事实 | 14:05 开始，影响全部下单 |
| 约束和禁止事项 | 主库不能重启（尽量保留用户的原话） |
| 已排除的方向和理由 | 网络：网络组确认链路正常 |
| 已经做过的动作 | 查过监控、错误日志、会话列表 |
| 待办和要通知的人 | 结论同步到 #db-oncall（还没发） |

再加两条：不要保留原始日志，只保留从中得出的结论；已做和待做要分开写。第二次压缩时，把上一份摘要也交给模型，在它的基础上更新，而不是从头再总结。

**完整记录另存一份。** 压缩替换的是发给模型的内容，原始对话要完整保存下来：出了问题能复盘，评测要用，摘要漏了什么也能找回来。Anthropic 2026 年 4 月介绍的 Managed Agents（Anthropic 托管运行 Agent 的服务，单元十二细讲）把这一点做成了架构：完整的事件日志存在会话里，上下文窗口只是从日志里取出来的一部分。压缩、清除、记忆都是不可逆的取舍；有了日志，需要时还能按位置把某一段原样取回来。

## 9.4 记忆：让下一次会话记得

压缩管的是一次会话之内。会话结束，messages 就清空了；用户的偏好、项目里不明显的约定、上次踩过的坑，下次还要重新交代。记忆就是把这些东西留到会话之外，作为下次能读到的上下文。

Anthropic 2026 年 11 月的《The components of agent memory》把记忆分成几层，从“每次都加载”到“用到才查”：

| 层 | 是什么 | 例子 |
|---|---|---|
| 注入的上下文 | 每次会话开始就放进输入的一小段 | `CLAUDE.md`；Claude Code 自动记忆的索引 `MEMORY.md`，只加载前 200 行或 25KB |
| 整理过的表示 | Agent 维护的知识，比如一个 wiki：一个对象一页，页面互相链接 | 每台数据库一页：负责人、历史故障、注意事项 |
| 笔记 | Agent 在会话里写下的观察和规则，一条一个文件 | “主库禁止重启（用户 11-25 说的）” |
| 原始记录 | 所有会话的完整日志，能搜索 | 9.3 里另存的那份原始对话 |

下面的层是上面的层的来源。文章还讲了一个环节，叫**做梦**（dreaming）：不在会话里做，而是离线读一遍原始记录和已有的记忆，改正写错的笔记、合并重复的、补上新的、把散落的笔记整理成 wiki，并决定哪些内容值得放进每次都加载的那一层。

learn-claude-code 把记忆拆成存储、召回、提取、整理四件事，做梦就是其中的“整理”，只是挪到了会话之外。Claude Managed Agents 2026 年 4 月上线了文件形式的记忆，5 月起可以试用做梦。

这篇文章的几个实验，比“记忆该怎么写”的规则更有用：

- **告诉模型记忆是干什么用的，别规定怎么用。** 在一个数据库问答基准上，每道题开一个新会话，记忆目录跨会话保留：有了记忆，Opus 5.5 的平均得分从 0.655 升到 0.838。可要是再规定“只记录失败”，记忆带来的提升反而缩水（Opus 5 上少了 0.234，Opus 4.7 上少了 0.150）。强模型自己判断什么值得记，比固定的规则好。
- **弱一些的模型要多一句指点。** Sonnet 4.6 有了记忆只从 0.330 升到 0.364，它不到一半的时候会先去读记忆；提示里明确要求“先读记忆，再验证自己的猜想”，升到 0.641。
- **每次都加载的那一层要小。** 它每次都占 token，一条写错的笔记会被带进以后每一次会话；说明文件越长，模型越不照着做。
- **多个 Agent 同时写，一个对象一页。** 几个 Agent 往同一张汇总表里写合同条款，互相覆盖，57 条事实只留下 41 条；改成每份合同一页、原文引用条款，57 条都在。
- **整理过的 wiki 补充搜索，不替代搜索。** 在一个约 35 万个文件的资料库上，wiki 加搜索答对 54% 到 61% 的评分项，只用搜索是 53%，只用 wiki 是 13% 到 48%；wiki 加搜索每题还省了约 2 万 token。

什么该记，什么不该记：

| 该记 | 不该记 |
|---|---|
| 用户的偏好和工作方式（“改动先给方案再动手”） | 代码、文档、git 历史里能直接查到的东西 |
| 用户给过的纠正，以及为什么 | 只和这一次对话有关的临时信息 |
| 项目里不明显的约定和约束（“主库禁止重启”） | 密码、令牌、个人隐私 |
| 外部资料在哪（“告警看板在某某地址”） | 没有核实过的猜测 |

还有两件容易被忽视的事：

- **每条记忆都是一个预测：它预测这条事实以后还用得上、还是对的。** 记忆里说某个函数在某个文件里，可能已经被改名了；说某台库是主库，可能已经切换过。记下一条规则时，连同它是怎么验证的一起记；用之前用工具核实一遍，过期的及时更新或删掉。
- **记忆也是攻击面。** 注入的内容一旦写进 `CLAUDE.md` 或记忆目录，每次会话启动都会被重新加载，Anthropic 2026 年 5 月把这列为还没解决的威胁。生产里的记忆要能查到是哪个 Agent、哪次会话写的，能回滚、能删除，Managed Agents 的记忆就带着这样的审计记录。

记忆和下一单元的 RAG 都是“从外面取信息放进上下文”。区别在来源：记忆是 Agent 自己在和这个用户、这个项目打交道时攒下来的；RAG 检索的是外部现成的文档库。

## 9.5 上下文工程清单

按输入里的位置，从前往后：

| 位置 | 放什么 | 原则 |
|---|---|---|
| 系统提示词 | 身份、规则、项目说明 | 稳定、简短；放最前面，命中缓存（单元六） |
| 工具定义 | 这次任务用得上的工具 | 工具多了按需加载（单元七） |
| 记忆和知识 | 记忆索引、技能目录；用到时读全文 | 目录常驻，全文按需（单元五、9.4） |
| 历史 | 压缩后的摘要 + 最近一段原文 | 结构化压缩，按 token 保留（9.2、9.3） |
| 工具结果 | 合并、截断后的结果 | 在源头压缩，大的存文件留路径（单元四） |
| 当前状态 | 时间、预算、进度 | 放最后，不打断缓存（单元六） |

最后一条原则贯穿所有位置：**每加一样东西，问一句“模型这一轮真的需要它吗”。** 上下文里每多一段无关内容，就多一分钱、多一分延迟，也多一分把模型带偏的可能。

## 做项目时

- 每一轮记下输入的构成（系统提示词、工具定义、历史、工具结果各多少 token），定期看谁在膨胀。
- 工具输出在源头压缩；大结果存文件，上下文里留路径。
- 设定压缩阈值（窗口减去预留），按 token 保留最近的原文；压缩提示词列出必须保留的字段，尤其是约束和已排除项，尽量保留用户原话。
- 不要用简单截断处理长会话；如果必须截断，至少把用户说过的话单独保留。
- 原始对话完整另存，用于复盘和评测。
- 记忆分层：每次加载的只放一个短索引，笔记和 wiki 按需读，原始记录能搜；告诉模型记忆的用途，不规定死规则；定期离线整理；用之前核实，过期就删；记录每条是谁写的。
- Agent 声称做了的动作，以工具调用记录为准。

## 面试常问

**上下文太长了怎么办？**

先看谁占大头。我量过一段长排查对话，最后一轮 8.9 万 token 里，用户交代的关键事实只有一百多个，其余几乎全是工具的原始输出。所以第一步是在源头压缩工具输出；第二步是把旧的大结果存文件、上下文留路径；最后才让模型把更早的历史写成摘要，保留最近一段原文。我对比过四种策略：只留最近几条消息，交接里 6 个关键事实只写对两三个，而且 3 遍都编出了一次根本没发生的上线，还有两遍建议下一班回滚它；朴素的“总结一下”会漏掉“已排除”这类结论；列出必须保留字段的结构化摘要三遍都全对。

**压缩会丢信息，怎么降低风险？**

三点。压缩提示词明确列出不能丢的字段：用户给的事实、约束和禁止事项、已排除的方向、已做和待做；约束尽量保留用户原话。按 token 而不是按条数保留最近的原文，先压工具输出再压历史。完整的原始对话另存一份，出了问题能复盘，也能让模型需要时读回来。

**Agent 的长期记忆怎么设计？**

按 Anthropic 2026 年 11 月的说法分层：每次会话加载的只有一小段（项目说明、记忆索引），下面是 Agent 写的笔记、整理成的 wiki，最底层是能搜索的原始记录。召回靠索引加按需读取；整理可以离线做，读原始记录改正、合并、补充笔记，他们叫“做梦”。几个实测结论：告诉模型记忆的用途就够了，规定“只记录失败”反而让提升缩水；多个 Agent 同时写时一个对象一页，否则会互相覆盖；wiki 补充搜索、不替代搜索。只记查不到的东西：用户偏好、给过的纠正、不明显的约束；不记临时信息和敏感信息。每条记忆都是“以后还对”的预测，用之前要核实；记忆还会被注入污染，要能追溯是谁写的、能回滚。

## 自测

1. 一段长排查对话的最后一轮，输入里谁占大头？这对上下文工程意味着什么？
2. 截断、朴素摘要、结构化摘要，在实验里各写对了几个事实？截断以后模型做了什么？
3. 为什么说完整历史这次全对，也还是要压缩？
4. 一个好的压缩提示词要列出哪些字段？为什么约束要尽量保留用户原话？
