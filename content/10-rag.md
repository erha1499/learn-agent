# 单元十 RAG 和 Agentic RAG

本单元的核心：RAG 让模型回答它本来不知道的事：先检索相关资料，再照着资料回答。效果的上限是检索：资料没取回来，模型要么说不知道，要么编一个。经典 RAG 检索一次，由程序决定查什么，便宜、可控；Agentic RAG 把检索做成工具，让模型自己决定搜几次、换什么词，能补上一次检索漏掉的东西，代价是几倍的调用和 token。先把检索和评测做好，再决定要不要交给 Agent。

**学完这个单元，你能：**

- 讲清 RAG 的流程：切块、建索引、检索、重排、生成，每一步影响什么。
- 用实验数据比较不检索、经典 RAG、Agentic RAG 的效果和成本，判断什么时候值得用 Agentic RAG。
- 把检索和生成分开评测，说出 RAG 常见的失败和对策。

单元九的记忆是 Agent 自己攒下的信息。更多时候，Agent 需要的知识在现成的文档里：公司的规定、资产台账、过去的故障复盘。模型的训练数据里没有这些，不给它，它就只能编。知识不一定都要走 RAG：少量、能枚举的知识（比如按问题类型整理的排查手册）做成技能按需加载就够了；本单元用一个小知识库演示知识多、问题五花八门时的做法。先看不给资料会怎样，再拆开 RAG 的流程、比较几种检索器，然后用实验比较经典 RAG 和 Agentic RAG，最后讲怎么评、怎么选。

## 10.1 不给资料：说不知道，或者编一套规定

`examples/mini_kb/` 是一个虚构公司的小知识库，18 篇文档：资产台账（每台库的负责人、从库、备份时间）、各团队值班群、规定（主库重启、大表 DDL、连接池上限）、三篇故障复盘、几份排查手册。9 道题全是这家公司内部的事，模型不可能预先知道。

跑 `examples/u10_rag.py`，先不给任何资料直接问，每题 2 遍：

| 题型 | 例题 | 不检索时答对 |
|---|---|---|
| 单跳 | “order-mysql-01 的负责人是谁？” | 0/4 |
| 单跳，有冲突 | “报表库每天几点做全量备份？”（统一策略是 01:00，报表库例外是 03:30） | 0/2 |
| 单跳，别名 | “库存那台库的从库叫什么？” | 0/2 |
| 多跳 | “pay-mysql-03 的负责人所在的团队，值班群是哪个？” | 0/2 |
| 多跳，有更新 | “之前连接数打满的事故后来定了什么规范？现在连接池上限是多少？”（规范后来改过一次） | 0/2 |
| 换了说法 | “数据库写不进去但读没问题，以前遇到过吗？”（复盘里写的是“binlog 撑满数据盘”） | 0/2 |
| 桥接多跳 | “order-mysql-01 的负责人还负责哪台数据库？”（要先查到负责人是谁，再拿人名去找） | 0/2 |
| 没有答案 | “cache-redis-02 的 maxmemory 配置是多少？”（知识库里没有） | 2/2 |

大部分题它都老实说了“不知道”，这比编要好。但问到大表 DDL 的规定时，它 2 遍都写了一套详细的“公司规定”，比如要走 ITSM 工单、金融核心库要经架构委员会会签、工作日 07:00 到 22:00 禁止执行；上一轮试跑时还编过一个内部文档编号和一个公司 wiki 链接。这些都不存在。规定类的问题有大量“看起来对”的通用写法，模型最容易在这里编。

## 10.2 RAG 的流程

RAG（检索增强生成）分两段：先把资料整理成可检索的样子，再在每次提问时取回相关的部分交给模型。

| 步骤 | 做什么 | 影响什么 |
|---|---|---|
| 切块 | 把长文档切成段落大小的块，块里带上标题等上下文 | 块太大，取回来一堆无关内容；块太小，一个事实被切成两半。常见做法是按标题和段落切，检索小块、交给模型时换成它所在的大块（父子块） |
| 建索引 | 关键词索引（BM25）和/或向量索引（把文字变成一串数字，意思相近的文字数字也相近） | 决定能不能“按意思”找到：用户说“写不进去”，文档写的是“磁盘写满” |
| 检索 | 按问题找出最相关的若干块 | 召回不到的，后面全白费 |
| 重排 | 用一个更精细的模型给候选块重新打分，只留最相关的几块 | 提高前几块的质量，省上下文 |
| 生成 | 把取回的块和问题一起交给模型 | 提示词要求：只根据资料回答、注明出处、资料里没有就说没有 |

本单元的知识库很小，每篇文档就是一个块，没有用重排，重点放在检索和生成上。

## 10.3 三种检索器

同一批题（8 道有答案的），三种检索器各取前 3 篇：

| 检索器 | 怎么找 | 第 1 篇就是该看的文档 | 前 3 篇包含全部该看的文档 |
|---|---|---|---|
| BM25 | 按字面重合打分（中文按两字片段切） | 7/8 | 7/8，漏了桥接多跳那题 |
| 向量 | 百炼 text-embedding-v4，按意思相近打分 | 7/8 | 8/8 |
| 融合 | 两种排名用 RRF 合并（每篇文档按它在两个排名里的位置取倒数再相加） | 8/8 | 8/8 |

读这张表抓住两点：

- **字面和意思各有盲区，融合最稳。** BM25 擅长人名、实例名、编号这类精确的词；向量擅长换了说法的问题。生产里常用两者融合，再加一步重排。
- **知识库这么小，检索本来就容易。** 18 篇文档取前 3 篇，等于取了六分之一。文档一多、相似的文档一多（每台库都有一篇格式相同的台账），差别才会放大。所以 RAG 的评测一定要用和线上规模相近的知识库。

## 10.4 经典 RAG 和 Agentic RAG

两种用检索的方式：

- **经典 RAG**：程序拿用户的问题检索一次（这里用向量检索），把前 3 篇全文放进提示词，模型调用一次。
- **Agentic RAG**：把检索做成两个工具，`search_kb(query)` 返回最相关 3 篇的编号、标题和开头，`read_doc(doc_id)` 读全文。模型自己决定搜什么、搜几次、读哪篇（单元三的循环）。

9 道题，每题 2 遍：

| | 答对 | 每题调模型 | 每题 token |
|---|---|---|---|
| 不检索 | 2/18 | 1 次 | 132 |
| 经典 RAG | 18/18 | 1 次 | 406 |
| Agentic RAG | 18/18 | 3.6 次 | 2,514 |

看一下那道桥接多跳题，两种方式是怎么做对的：

- **Agentic RAG** 先搜“order-mysql-01 负责人”，读到负责人是周岚，再搜“周岚 负责的数据库”，找到了 user-mysql-04。这就是“检索结果决定下一次检索”。
- **经典 RAG** 也答对了，但有运气成分：向量检索恰好把 user-mysql-04 的台账排在了第 3 位。BM25 排第 3 的是一篇复盘，如果用的是 BM25，资料里就不会有 user-mysql-04，模型只能说不知道或者猜。

读这张表抓住三点：

- **给对资料，是 0 分和满分的差别。** 不检索只对了“没有答案”那一题；有了检索，两种方式都全对。
- **在这个知识库上，Agentic RAG 多花了 6 倍的 token，准确率没有提高。** 一次检索已经够用时，让模型自己搜只是多了几轮调用。
- **Agentic RAG 的价值在一次检索不够的时候：** 桥接多跳（第二跳的关键词要从第一跳的结果里来）、问题含糊需要换说法再搜、知识库大到前几篇经常不对。这时它能自己补救，经典 RAG 只能靠运气。

## 10.5 怎么评 RAG

RAG 出错只有两种可能：资料没取回来，或者取回来了但没用对。所以要**分开评**：

| 评什么 | 指标 | 怎么判 |
|---|---|---|
| 检索 | 召回：该看的文档在不在前 k 篇里；排序：第 1 篇对不对 | 每道题标出“该看哪几篇”，用程序算 |
| 生成：答对 | 答案里有没有关键事实 | 能用程序判的用程序（编号、数字、名字） |
| 生成：忠于资料 | 答案里的每个说法，资料里有没有依据 | 大模型评委或人工抽查 |
| 生成：引用 | 注明的出处文档是不是真的包含这句话 | 程序核对编号，评委核对内容 |
| 生成：没有就说没有 | 知识库里没有答案的题，有没有如实说 | 专门放几道这样的题 |

只看最终答对率，分不清是检索的问题还是生成的问题，也就不知道该改哪一边。

打分规则本身也要核对，这次又遇到了一回：第一版规则判断“换了说法”那题，只要答案里出现 binlog 就算对，结果不检索的模型因为给了一段泛泛的排查建议（里面提到了“检查 binlog 状态”），被误判成答对。改成要求答出这次复盘里的具体处置（PURGE 清理、扩容到 2TB）以后才正确。

## 10.6 什么时候用什么

| 知识的样子 | 用什么 | 例子 |
|---|---|---|
| 少量、结构化、能枚举 | 精确查表，或者做成技能按需加载 | 按问题类型整理的排查手册（单元五的技能） |
| 大量非结构化文档，问题五花八门 | RAG：融合检索 + 重排 | 公司知识库、产品文档、客服问答 |
| 一次检索经常不够（多跳、要换说法） | Agentic RAG：检索做成工具 | 深度调研、跨文档推理 |
| 代码仓库这类变化快、本身就有结构的资料 | 让模型用 grep、glob、读文件自己找，不建索引 | Claude Code：据它的负责人 2025 年 5 月在一档播客里的说法，最早用本地向量库做 RAG，后来改成让模型自己搜；理由是不用维护索引、没有索引带来的安全问题，代价是更多调用和 token，他也承认这个判断主要靠体感，内部评测不多 |
| 总量不大、每次都要全看 | 直接放进上下文 | 一份几千字的规范 |

几条经验：

- **先评检索，再评生成。** 检索召回上不去，换多好的模型、写多好的提示词都没用。
- **规定、配置这类“必须准确”的问题，一定要求注明出处**，并由程序核对出处存在；资料里没有就让它明确说没有，不要猜。
- **知识要有更新机制。** 实验里“连接池上限”改过一次（30 改成 25），两份文档都在库里。检索到旧文档、没检索到修订，就会答错；文档里写清生效日期，过期的及时下线。

## 做项目时

- 先准备评测集：每道题标出答案和“该看哪几篇”，放几道没有答案的题。
- 切块按标题和段落，块里带上标题；检索小块、交给模型时可以换成父块。
- 检索用 BM25 和向量融合，再加重排；用和线上规模相近的知识库评召回。
- 生成的提示词要求只根据资料回答、注明出处、没有就说没有；程序核对出处。
- 先用经典 RAG；一次检索经常不够（多跳、要换说法、召回不稳）时，再考虑 Agentic RAG，并用评测确认多花的 token 买到了准确率。
- 检索、生成分开评；打分规则拿原文逐条核对。
- 文档写清生效日期，修订后下线旧版本。

## 面试常问

**RAG 的流程是什么？各步有什么讲究？**

两段。离线把文档切块、建索引；在线按问题检索、重排、把前几块和问题一起交给模型生成。切块按标题和段落，块里带标题，常用父子块：检索小块，交给模型时换成大块。索引用 BM25 和向量融合：BM25 擅长实例名、编号这种精确的词，向量擅长换了说法的问题，我在一个小知识库上试过，融合后第一篇命中率最高。生成时要求只根据资料回答、注明出处、没有就说没有，出处由程序核对。

**RAG 和 Agentic RAG 有什么区别？什么时候用 Agentic RAG？**

经典 RAG 由程序拿问题检索一次，便宜可控；Agentic RAG 把检索做成工具，模型自己决定搜什么、搜几次。我实测 9 道内部知识题：不检索只对了“没有答案”那一题；经典 RAG 全对，每题 400 token；Agentic RAG 也全对，但每题 2,500 token、3.6 次调用。它的价值在一次检索不够的时候，比如桥接多跳：要先查到负责人是谁，再拿人名去找第二篇，Agentic RAG 会自己搜第二次，经典 RAG 只能靠第一次检索碰巧带上。所以先用经典 RAG，评测发现一次检索经常不够时再升级。

**怎么评测一个 RAG 系统？**

检索和生成分开评。检索看召回和排序：每道题标出该看哪几篇，算前 k 篇里有没有、第一篇对不对。生成看答对、忠于资料、引用是否正确、没有答案时是否如实说没有；能用程序判的用程序，其余用评委加人工抽查。还要放几道知识库里没有答案的题，测它会不会编。只看最终答对率，分不清问题出在检索还是生成。
