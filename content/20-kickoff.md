# 单元二十 立项：先定标准再写代码

本单元的核心：写第一行 Agent 代码之前，先写下怎么算成功、答错和不答各有多贵、它能做到哪一步，再量最简单的方案能做到多少。最简单的方案做不到的部分，才是 Agent 要挣的钱；答错和不答的代价比，决定了要不要给 Agent 留“不知道”的出口、程序要不要把关。这些不先写下来，后面每一个设计选择都没有依据。

**学完这个单元，你能：**

- 在写 Agent 之前量出最简单方案的基线，判断这个场景要不要 Agent，以及你的评测集能不能区分这些方案。
- 把“答错和不答哪个更贵”写进标准，用它决定要不要让 Agent 说不知道、要不要加程序的门，以及怎么打分。
- 写一份立项单：任务、现状和基线、记分卡、出错代价、自主程度、评测计划、上线和叫停的条件。

前三部分把 Agent 拆成零件讲：循环、harness、工具、上下文、安全、评测。第四部分把它们装成一个能交给用户的系统，这一单元是第一步：动手之前先把标准定下来。先看两个实验：最简单的方案能做到多少，答错和不答哪个更贵；再讲立项单的每一项，最后讲成功标准怎么写、权限怎么放。

## 20.1 先看现象：最简单的方案能做到多少

跑 `examples/u20_baselines.py`。值班排障有三种做法：

- **规则**：不调模型。程序把四个数据源都查一遍，超时就重试一次，按固定阈值判根因：网络丢包或延迟高就是网络问题，错误日志里有磁盘满就是磁盘写满，依次往下。
- **一次调用**：程序同样把四个数据源都查一遍，再把用户的问题和全部结果一次交给模型，让它下结论。这是单元三说的 Workflow。
- **Agent**：单元十三的 Agent，自己决定查什么、查几次。

两套题。原题是迷你评测集的 20 条用例。规则是我写的，我知道这套题是怎么造的，所以规则在原题上的成绩是乐观的上限。为了公平，规则写定以后，我又造了 10 条“换说法”的题：根因不变，证据换成规则没预料到的写法和数值，比如 MySQL 的另一种磁盘满报错“Disk full; waiting for someone to free some space”，而不是 errno 28；丢包率不高但重传率 14%；扫了 5,200 万行、却只跑了 9.8 秒的查询，刚好压在规则的阈值下面。这些题是冲着规则的盲区造的，对规则也不公平，正好说明规则怕什么。

| 方案 | 原题 | 换说法 | 每次的 token | 每次耗时（中位数） |
|---|---|---|---|---|
| 规则 | 100% | 0% | 0 | 几毫秒 |
| 一次调用 | 94.0% | 84.0% | 1,203 | 10.5 秒 |
| Agent | 86.5% | 84.0% | 3,634 | 10.9 秒 |

一次调用每条跑 5 遍；Agent 在原题上用的是单元十七录下的 200 次运行，在换说法的题上每条跑 5 遍。

读这张表抓住三点：

- **规则在写它的人见过的题上满分，换个说法就全错。** 它只认得写它的人预料到的写法和阈值。原题满分还说明另一件事：这套评测集对规则来说太规整了。立项时如果最笨的方案就能满分，要么这个场景不需要模型，要么评测集没装进真正难的部分：写法的变化、没见过的故障、数据源出错。
- **在这套题上，程序取全数据加一次调用，比 Agent 还好、还便宜。** 原题 94.0% 对 86.5%，token 只有三分之一。按用例配对，差 +7.5 ± 11.0 个点，区间包含 0；差别集中在两条：C15 是注入，转发的消息让 Agent 跳过取证，一次调用不存在“跳过”，程序已经把数据都取来了（+100 个点）；C16 是关键数据源第一次超时，程序会重试，Agent 只答对一半（+50 个点）。Agent 多出来的自由，在这里只带来了两种出错的方式。
- **模型的价值在读懂没见过的写法。** 换说法的题上两种模型方案都是 84%，规则是 0。Agent 自己决定查什么的价值，在这套只有四个数据源的题里没有体现出来；数据源多到没法每次都取全、下一步查什么取决于上一步看到了什么时（单元三），才轮到它。单元三里 Workflow 输给 Agent，是因为写死的步骤只查了两个数据源，漏了错误日志：关键不在 Workflow 还是 Agent，而在写死的步骤能不能覆盖全部证据。

所以立项的第一件事：在评测集上量出最简单方案的成绩。它就是基线，Agent 要比它好，才值得多花的钱和多出来的风险。Anthropic 2024 年 12 月的《Building effective agents》说得更直接：先找最简单的方案，只在必要时增加复杂度，这可能意味着根本不做 Agent。

## 20.2 答错和不答，哪个更贵

跑 `examples/u20_abstain.py`。比较几个版本：

- **A**：单元十三的 Agent，总要给出一个根因。
- **U**：系统提示词加一句：关键数据查不到、或者证据不足以确定根因时，不要猜，回答“根因: UNKNOWN”，说明缺哪些数据。这时转人工。
- **加门**：不改 Agent，程序在它交卷时检查一遍：结论对应的关键数据源（磁盘写满对应错误日志，网络问题对应网络检查，以此类推）一次都没成功返回过，就把结论改成 UNKNOWN。这就是单元十九的“结论缺关键证据”，当成单元四的提交门来用。

每个版本在两种情况下各跑 100 次（20 条用例 × 5 遍）：正常，以及错误日志服务宕机（每次都返回 504）。磁盘写满的唯一硬证据在错误日志里，宕机时它其实查不出来。

每 100 次里，答对 / 答错 / 转人工：

| 版本 | 正常 | 错误日志宕机 |
|---|---|---|
| A 总要给结论 | 78 / 22 / 0 | 74 / 26 / 0 |
| U 允许说不知道 | 87 / 10 / 3 | 76 / 16 / 8 |
| A 加门 | 71 / 17 / 12 | 62 / 21 / 17 |
| U 加门 | 84 / 5 / 11 | 74 / 11 / 15 |

A 在这里是 78%，比单元十七的 86.5% 低，主要差在 C20：单元十七里它 10 遍全对，这批 5 遍错了 4 遍。这批每条只跑了 5 遍，单元十七讲过这种波动。按用例配对，正常情况下 U 比 A 少答错 12.0 ± 11.5 个点。

读这张表抓住三点：

- **留一个出口，答错少了一半多，转人工只多了 3%。** 正常情况下，U 说不知道只有 3 次，都在 C16（错误日志第一次超时）；答错却从 22% 降到 10%。这句话让它整体更谨慎了，代价是每次多用 21% 的 token（3,500 到 4,248）。
- **模型不太知道自己不知道。** 宕机时磁盘写满的 20 次，U 说了 8 次不知道，另外 11 次照样答成锁等待。只靠提示词不够，要程序把关：门把 C15 那种一次工具都没调就下的结论，全都改成了不知道。
- **门也会把一些答对的改成转人工。** 没拿到关键证据却答对的，本质是猜对的（单元十三的“结论对、过程站不住”）；门不区分，一律转人工。值不值得，看答错比转人工贵多少。

把每个会话的代价记成：答对 0，转人工 1，答错 r（答错比转人工贵 r 倍）：

| 答错的代价 | A | U | A 加门 | U 加门 | 最划算 |
|---|---|---|---|---|---|
| r = 1，正常 | 0.22 | 0.13 | 0.29 | 0.16 | U |
| r = 3，正常 | 0.66 | 0.33 | 0.63 | 0.26 | U 加门 |
| r = 10，正常 | 2.20 | 1.03 | 1.82 | 0.61 | U 加门 |
| r = 3，宕机 | 0.78 | 0.56 | 0.80 | 0.48 | U 加门 |

答错和转人工一样贵时，U 最好，门多转出去的人工不值得；答错贵三倍以上，加门就划算了。值班场景，一次错误的结论会把排障带偏、延误恢复，通常比多叫一次人贵得多。

这个比例必须在立项时写下来，因为它决定了三件事：要不要给 Agent 留“不知道”的出口，程序的门设多严，以及打分器怎么算。单元十五的打分器只有对和错，会把诚实的“不知道”当成答错，反过来惩罚了更好的版本；结果要分成三种：对、错、不知道。

## 20.3 立项单：动手之前写下的八件事

把前两节的结论，连同前面几个单元的做法，写成一张立项单。右边一列是值班 Agent 的例子，量级、人工耗时和门槛是示意，换成你的场景：

| 项 | 写什么 | 值班 Agent 的例子 |
|---|---|---|
| 用户和任务 | 谁用、输入什么、要什么输出、一天多少次 | 业务开发在群里问“这个库是不是有问题”；输出根因、证据、建议；每天几十次 |
| 现状 | 现在谁在做、花多久、做得多准 | 值班 DBA 人工排查，一次十几分钟 |
| 基线 | 最简单的方案在评测集上能做到多少 | 规则：原题 100%、换说法 0%；取全数据加一次调用：94% 和 84% |
| 记分卡 | 每个维度一个门槛，全过才算过（单元十五） | 答对率不低于 90%、答错率不高于 5%（按用例算，每条跑 3 遍）；注入用例一次都不外发；每次不超过 6,000 token；耗时 P90 不超过 60 秒 |
| 出错代价 | 答错、转人工、太慢各有多贵，比例是多少 | 答错一次约等于转人工 5 次：留“不知道”的出口，程序检查关键证据 |
| 自主程度 | 只建议、要批准才执行、白名单内自己执行 | 只读查询加建议；重启、改配置要人批准（单元十一） |
| 评测计划 | 题从哪来、多大、怎么打分、谁标注 | 20 条构造的用例起步，加上换说法和数据源宕机的题；对、错、不知道分开计；线上失败回流（单元十四） |
| 上线和叫停 | 达到什么就灰度，出现什么就回滚，什么情况下换方案 | 记分卡全过才灰度；答错率超过门槛就回滚；如果取全数据加一次调用就能达标，不做 Agent |

最后一行的“叫停”常被忘掉。立项时就写下：什么结果出现，说明这个方向不对。比如这一单元的实验，在这四个数据源上，答案是先做一次调用的版本。

## 20.4 标准怎么写才算数

**每一条都要能量。** Anthropic 的文档说，好的成功标准要具体、可测、能达到、和用途相关。“输出要安全”不算标准；“10,000 次里被内容过滤器标为有害的不到 0.1%”才算。他们举的情感分类例子是：在 10,000 条留出的推文上 F1 不低于 0.85，比现在的基线高 5%。门槛是对着基线定的，这正是 20.1 要先量基线的原因。

**几个维度一起定。** 文档列了常见的维度：任务完成得怎么样、同样的输入结果是否一致、是否切题、语气风格、隐私、能不能用好给它的上下文、延迟、价格；并且说多数场景要同时在几个维度上定标准。他们的例子里有一条值得注意：90% 的错误只造成不便，而不是严重的错误。错误也分轻重，这就是 20.2 的代价比。

**先写评测题，再写 Agent。** Anthropic 2026 年 1 月的《Demystifying evals for AI agents》把这叫评测驱动的开发：在 Agent 做得到之前，先把期望的行为写成评测题。原因是两个工程师读同一份需求，对边界情况的理解常常不一样；写评测题的过程，本身就在检验需求是否具体到能开工。几条做法：

- 起步用 20 到 50 条来自真实失败的题就够了，越晚开始越难补。
- 一道好题，两个领域专家各自判，结论应该一样；判不一样，先改题。
- 每道题配一个参考答案，证明它做得出来、打分器配置正确。
- 既放“应该做”的题，也放“不该做”的题，比如既测该查的有没有查，也测不该转人工的有没有乱转。

**写好的标准，干活的人不能改。** Anthropic 2025 年 11 月的长任务 harness 也是这个思路：开工前，先由一个初始化 Agent 把需求展开成一份 JSON 格式的功能清单（他们的例子有 200 多条），每条带验证步骤和“是否通过”，初始都是未通过；之后干活的 Agent 只能改“是否通过”这一项，删改清单是不允许的，否则功能会悄悄漏掉。对人也一样：标准在动手之前写下，做的过程中只记录过没过，不改门槛。

## 20.5 权限先窄后宽

立项单里的“自主程度”，从最窄的开始：

1. **只读加建议**：Agent 查数据、给结论和建议，人来执行。
2. **要批准才执行**：Agent 提出动作，人点确认（单元十一）。
3. **白名单内自己执行**：低风险、可撤销的动作自动做，其余仍要批准。

往上走一级，要有证据：评测集上的成绩、线上的轨迹和指标（单元十九）。Claude 平台 2026 年 10 月的文档给的建议也是先看它的轨迹，等它证明可靠了再放宽权限。用户自己也是这样做的：Anthropic 2026 年 2 月分析了约 50 万个 Claude Code 会话，新用户大约 20% 的会话开着全自动批准，用到 750 个会话时超过 40%：信任是随着使用积累起来的。

《Building effective agents》列了适合交给 Agent 的任务的几个特点：既要对话又要行动，有清楚的成功标准，能形成反馈回路，有人监督。立项单的前几项，就是在逐条确认这些。

## 做项目时

- 写第一行代码之前，先把立项单写完：用户和任务、现状、基线、记分卡、出错代价、自主程度、评测计划、上线和叫停的条件。
- 先在评测集上量最简单的方案：规则、取全数据加一次调用。Agent 要比它们好，才值得做。
- 评测集要能区分方案：最笨的方案能满分，就往里加写法的变化、没见过的故障、数据源出错。
- 写下答错和不答的代价比；据此决定要不要留“不知道”的出口、程序的门设多严；打分分成对、错、不知道三种。
- 别只靠提示词让模型承认不知道，关键证据由程序检查。
- 成功标准要具体、可测、能达到、和用途相关，门槛对着基线定；几个维度一起定，全过才算过。
- 先写评测题再写 Agent；标准写定以后，做的过程中不改门槛。
- 权限从只读加建议开始，凭评测成绩和线上证据一级一级放宽。

## 面试常问

**接到一个 Agent 需求，写代码之前你会做什么？**

先写立项单：谁用、要什么输出、现在人怎么做、多准多久；成功标准写成带门槛的记分卡，几个维度一起定；答错、不答、太慢各有多贵；Agent 能做到哪一步，先只读加建议；评测集先建，起步二三十条；以及什么情况叫停。然后先量最简单的方案。我做过一次：值班排障里，程序把四个数据源全取来、交给模型一次下结论，答对率 94%，比 Agent 的 86.5% 还高，token 只有三分之一；Agent 多出来的自由只带来了被注入带着跳过取证、超时不重试两种错误。这种情况下我会先上一次调用的版本。

**怎么判断一个场景要不要用 Agent？**

看最简单的方案在评测集上能做到多少，以及差在哪。规则能做到，就用规则；取全数据加一次调用能做到，就用 Workflow。Agent 的价值是按中间结果决定下一步，只有数据源多到没法每次取全、下一步取决于上一步看到什么时才值得。还要检查评测集本身：我写的规则在原题上满分，换个说法就全错，说明原题太规整，没装进真正难的部分。

**Agent 什么时候应该说“不知道”？**

取决于答错比转人工贵多少，这要在立项时写下来。我测过：加一句“证据不足时不要猜”，答错从 22% 降到 10%，转人工只多 3%；再加一道程序的门，结论对应的关键数据源没成功返回过就转人工，答错降到 5%，转人工到 11%。答错和转人工一样贵时，只加提示词最好；答错贵三倍以上，加门更好。另外模型不太知道自己不知道：错误日志宕机时，它 20 次里只有 8 次说不知道，11 次照样答错，所以关键证据要由程序检查。打分也要改成对、错、不知道三种。

## 自测

1. 规则、一次调用、Agent 三种方案，在原题和换说法的题上各做到多少？规则为什么原题满分、换说法全错？
2. 取全数据加一次调用，为什么在原题上比 Agent 好？好在哪几条用例？这说明 Agent 什么时候才值得做？
3. 如果最简单的方案在你的评测集上就满分，可能说明什么？该怎么办？
4. 允许 Agent 说“不知道”以后，答对、答错、转人工各变了多少？它真的知道自己什么时候不知道吗？
5. 程序的“门”检查什么？它为什么会把一部分答对的也变成转人工？
6. 答错比转人工贵 1 倍、3 倍时，哪个版本最划算？为什么立项时要写下这个比例？它还影响打分器的什么？
7. 立项单要写哪几项？“叫停的条件”为什么也要事先写？
8. 好的成功标准有哪几个特点？为什么要先写评测题再写 Agent？Agent 的权限凭什么一级一级放宽？
