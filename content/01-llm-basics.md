# 单元一 大模型：一个按概率续写文字的零件

本单元的核心：大模型是一个“按概率一个字一个字往下写”的零件。每次调用都要花钱、花时间，同样的输入不保证同样的输出，写出来的东西也不保证是真的。后面所有的 Agent 设计，都是在给这个零件的脾气打补丁。

**学完这个单元，你能：**

- 算清一次调用用了多少 token、花了多少钱，说出为什么 Agent 的花费九成以上在输入上。
- 解释 temperature 和 seed 怎么影响输出，知道 temperature 设成 0 也不保证每次一样，以及这对评测意味着什么。
- 认出 Agent 里幻觉的典型样子，说清为什么在提示词里要求“别编”不够，要靠程序核对。

做 Agent 之前，先认识它最核心的零件。这里先把 Agent 粗略理解成“一个反复调用模型、按模型的要求去调用工具、直到把任务做完的程序”，单元二、三会从零把它搭出来。本单元从一次调用讲起：先看它吃进去什么（token），再看它花掉什么（钱和时间），然后看它吐出来的东西有多可靠（随机、截断、编造）。最后把这些放进一个真实的 Agent 里，看它们被放大成什么样。

文中的结果都是真实调用跑出来的（qwen-plus，2026-11-23）。代码在 `examples/`，加 `--replay` 不调模型、直接看录好的结果。

## 1.1 一次调用发生了什么

调大模型就是发一个 HTTP 请求：把一组消息发过去，拿回一段文字。

```python
from _llm import chat          # examples/_llm.py，只用标准库
r = chat([{"role": "system", "content": "你是数据库值班助手"},
          {"role": "user", "content": "连接数打满了怎么办？"}])
print(r["text"], r["usage"])   # usage 里是这次用了多少 token
```

消息有三种角色：

- **system**：给模型的长期设定（你是谁、规则是什么）。
- **user**：用户说的话。
- **assistant**：模型之前说过的话。

模型拿到消息后做的事，可以理解成“接龙”：先把文字切成一个个 **token**，然后反复预测“下一个 token 是什么”，直到写完或者到了长度上限。

记住一个后面反复用到的事实：**模型是无状态的**。它不记得上一次调用说过什么。所谓多轮对话，是程序每一轮把之前的全部消息再发一遍。

## 1.2 token：模型按什么计数

模型不按字、也不按词计数，按 token 计数。token 是分词器切出来的片段，可能是一个汉字、半个英文单词、一个标点。

跑一下 `examples/u01_tokens.py`：同样的意思用不同的写法，各占多少 token？

| 内容 | 字符数 | token | 每个 token 几个字符 |
|---|---|---|---|
| 中文：数据库连接数打满，应用报错 Too many connections…… | 46 | 18 | 2.56 |
| 英文：The database ran out of connections…… | 105 | 20 | 5.25 |
| JSON：`{"root_cause_id": "MYSQL_MAX_CONNECTIONS", ...}` | 87 | 32 | 2.72 |
| 日志：`2026-11-21 14:05:31 [ERROR] HikariPool-1 ...` | 104 | 46 | 2.26 |
| 数字：`12345678901234567890` | 20 | 20 | 1.00 |

另外，空消息本身也占 8 个 token，这是对话模板里的角色标记和分隔符。

读这张表抓住三点：

- 英文大约一个单词一个 token；这句中文 46 个字占 18 个 token。
- 符号多的内容（JSON、日志、代码）特别占 token；这个模型的分词器把数字一位一个 token 地切。
- Agent 每天处理的正好就是日志、JSON、工具返回值，所以它的 token 消耗比聊天大得多。

token 重要，是因为三件事都按它算：

1. **钱**：按输入 token 和输出 token 分别计价。
2. **上下文窗口**：一次调用里，输入加输出不能超过一个上限。不同模型从几万到上百万 token 不等，以模型文档为准。
3. **速度**：输出是一个 token 一个 token 生成的（见下一节）。

## 1.3 钱和时间花在哪

跑 `examples/u01_latency.py`：同一个模型，一次只要一句话，一次要五百字，流式调用，记下“第一个字到达”和“全部收完”的时间。

| | 输出 token | 首字时间 | 总时间 | 生成速度 |
|---|---|---|---|---|
| 短回答 | 46～51 | 0.53～0.65 秒 | 1.7 秒左右 | 约 43 token/秒 |
| 长回答 | 553～560 | 0.44～0.71 秒 | 12.6～13.0 秒 | 约 45 token/秒 |

两件事一眼可见：

- **首字时间**和回答长短无关，都在半秒左右。这是模型读完输入、开始写之前的准备时间。
- **总时间**几乎和输出长度成正比：每秒大约写 45 个 token，写 560 个就要 13 秒。

原因是模型处理输入和输出的方式不一样：

- **输入**是一次性并行读完的，所以快、也便宜。
- **输出**只能一个接一个地生成：每写一个 token，都要基于前面所有内容再算一遍。所以慢，也更贵。

以阿里云百炼的 qwen-plus 为例（2026-11 公开价目，以控制台为准）：

| | 每百万 token |
|---|---|
| 输入 | ¥0.8 |
| 输出 | ¥2 |
| 输入命中缓存 | ¥0.08（一折） |

一次调用的花费 = 输入 token × 输入单价 + 输出 token × 输出单价。单次看都很便宜，1.7 节会看到它在 Agent 里怎么被放大。

### 深入一层（可跳过）：缓存为什么能打一折

模型读输入时，会为每个 token 算出一组中间结果（叫 KV cache）。如果两次调用的输入**开头完全相同**，后一次可以直接复用前一次算好的那部分，不用重算，服务商就按更低的价格收费。

关键是“开头完全相同”。如果每一轮都在输入的中间插入一段会变的内容（比如当前时间、最新状态），这段之后的部分就都对不上，缓存失效。所以设计提示词时，**不变的放前面，会变的放后面**。

## 1.4 同样的输入，不一样的输出

模型每写一步，给出的其实是“下一个 token 是谁”的概率分布，再从里面抽一个。控制怎么抽的有三个参数：

- **temperature**：调分布的尖锐程度。越低越集中在最可能的那个，越高越分散。
- **top_p**：只在概率加起来排前 p 的候选里抽，把长尾的离谱选项砍掉。
- **seed**：抽签用的随机数种子。种子一样、输入一样，抽出来的结果就一样。

跑 `examples/u01_sampling.py`：同一个问题问 10 遍，数一数有几种答案。

| 问法 | 设置 | 10 次里几种答案 |
|---|---|---|
| Redis 偶尔超时，最可能的原因？只回答一个词 | temperature=0，不传 seed | 1 种：网络×10 |
| 同上 | temperature=0.7，不传 seed | 1 种：网络×10 |
| 同上 | temperature=1.5，不传 seed | 1 种：内存×10 |
| 同上 | temperature=0.7，每次换 seed | 1 种：网络×10 |
| 同上 | temperature=1.5，每次换 seed | 3 种：内存不足×4、内存×4、网络×2 |
| 给这个问题写一个工单标题 | temperature=1.5，不传 seed | 1 种 |
| 同上 | temperature=1.5，每次换 seed | 2 种（只差一个空格） |

这张表有三个反直觉的地方：

1. **不传 seed 时，temperature 再高也每次一样。** 只有每次换 seed，temperature=1.5 才出现了 3 种答案。从实验看，百炼不传 seed 时，表现得就像固定了一个种子。所以想观察随机性，要自己控制 seed；只是把 temperature 调高，可能什么也看不到。
2. **分布很尖的时候，temperature 影响很小。** temperature=0.7 换了 seed，10 次还是“网络”。模型对这个答案非常确定，抽来抽去都是它。
3. **temperature 低，换来的是“稳定”，不是“正确”。** temperature=1.5 时的高频答案“内存”，和低温时的“网络”不一样，但哪个对，取决于具体故障，不取决于温度。

那 temperature 设成 0，是不是就完全确定了？跑 `examples/u01_determinism.py`：temperature=0、不传 seed，同一个问题问 30 次。

> 30 次里有 2 种不同的输出：29 次一样，1 次从第二个分句开始就换了说法（“大 key 扫描、BGSAVE 引发的 fork 阻塞……”变成“主线程被阻塞（如执行耗时命令、内存淘汰……）”）。

temperature=0 只是每一步都选概率最高的那个。但服务端并发计算时，浮点运算的顺序会有细微差别；两个候选的概率很接近时，这点差别就足以换掉一个字。一旦换掉一个字，后面的内容就跟着走上另一条路。

这对 Agent 的意义很直接：Agent 要连着调用模型十几次。第一步多查了一个指标、少查了一个日志，后面看到的证据就不同，结论也可能不同。**所以评测 Agent 不能只跑一遍**，这是单元十三的出发点。

## 1.5 输出会被截断，格式会出错

跑 `examples/u01_truncation.py`：让模型只输出一个 JSON 数组，列 5 个连接数打满的原因。

| max_tokens | finish_reason | 输出 | 能不能解析 |
|---|---|---|---|
| 40 | length | 40 个 token | 不能：字符串写到一半就断了 |
| 800 | stop | 236 个 token | **也不能**：第三个元素末尾把 `}` 写成了 `)` |

两件事：

- **finish_reason** 告诉你模型为什么停：`stop` 是自己写完了，`length` 是被长度上限截断了。截断的结果一定不完整，必须检查这个字段。
- **“只输出 JSON”是一个请求，不是保证。** 第二次模型正常写完了，格式照样是错的。

所以凡是要交给程序处理的输出，都要用程序校验格式，失败了重试或者兜底。更稳的做法是让模型通过“工具调用”提交结构化参数，按 JSON Schema 校验。这是单元二和单元六的内容。

## 1.6 幻觉：一本正经地编

**幻觉**是指模型输出看起来合理、实际上没有依据的内容。原因不难理解：模型做的是“写出最像下一句的话”，不是“查证后再说”。

先在简单问答里试试。跑 `examples/u01_hallucination.py`：给模型三行连接池报错日志，日志里**没有**最大连接数，问它最大连接数配的是多少。

> 直接问：10 次全部回答“无法确定，日志中没有提供这个配置”。加一句“资料里没有就说没有”：10 次全部回答“资料里没有”。

再问一个编出来的 MySQL 参数，10 次也都回答“不存在这个参数”。现在的模型在这类直接问答里，比几年前谨慎得多。

但在 Agent 里，情况不一样。下面是 oncall-agent-mvp 里一个取证子 Agent 的真实报告（运行 524）。子 Agent 是主 Agent 把“去查某个实例”这样的子任务，交给另一个独立的模型会话去做（单元五）：

```
[子Agent取证报告] 任务：查 refund-mysql-01 实例 12:00~15:00 是否存在 refund_v2 表……
摘要：refund-mysql-01 实例不存在，无法查询其表结构和权限；错误日志数据源不可用。
发现：
- E1(无效)：实例 refund-mysql-01 不存在，调用 get_instance_info 失败
- E2(无效)：实例 refund-mysql-01 不存在，调用 get_access_config 失败
- E3(无效)：[query_error_log] 调用失败：下游服务超时（504）……
本次产生的证据：无
```

四次调用全部失败，系统没有登记任何证据。可报告模板要求“每条发现都要引用证据编号”，模型就给失败的调用也编上了 E1、E2、E3。末尾的“(无效)”是程序发现这些编号不存在后加上的标记。

这种情况不是偶然：

| 实验（v2.1，各跑 3 遍） | 运行次数 | 子 Agent 报告里出现编造的编号 | 最终结论里引用了不存在的编号 |
|---|---|---|---|
| 复刻集 | 90 | 10 次 | 0 次 |
| 专项集（越权、注入） | 60 | 18 次 | 0 次 |
| 注入集 | 90 | 8 次 | 0 次 |

专项集里编得最多：18 次里有 16 次是越权用例，而越权用例一共只跑了 18 次。查询被权限拦下、返回失败，子 Agent 几乎每次都会编。最右一列是 0，是因为这个项目在提交结论这一步用程序核对了：引用的编号必须真的在证据库里，否则拒绝（单元四会讲这道“门”）。

读这张表抓住两点：

- **幻觉在长流程、固定格式、没有数据可写的地方最容易出现。** 简单问答里不明显，不代表 Agent 里不会。
- **挡住它的是程序，不是提示词。** 提示词里已经写了“不要编造”，模型照样编；程序核对之后，最终结论里一次都没有。

## 1.7 放到一个真实 Agent 里看

把前面几节合起来，看 oncall-agent-mvp 处理一条排障问题时，这个零件被用了多少次、花了多少钱（v2.1 在复刻集上跑 3 遍，共 90 次运行的平均值）：

| | 数值 |
|---|---|
| 主 Agent 调模型 | 9.8 次 |
| 子 Agent 调模型 | 11.8 次 |
| 一次调用里上下文的峰值 | 约 7,200 token |
| 一条用例累计输入 / 输出 | 111,120 / 5,726 token（输入占 95%） |
| 每条用例花费 | ¥0.071 |
| 耗时中位数 | 127 秒 |
| 输入命中缓存的比例 | 42%（改造前的简单版本是 65%） |

读这张表抓住三点：

- **单次调用的上下文只有 7,200 token，累计输入却有 11 万。** 原因就是 1.1 节说的无状态：二十多次调用，每次都把前面的对话重新发一遍。
- **钱主要花在输入上，所以缓存很关键。** 改造前的版本每例只要 ¥0.026，一个原因是它的缓存命中率高。改造后每一轮都在输入里插入最新的“系统状态”，很可能打断了缓存前缀（1.3 节的深入一层）。这一点在项目里还没验证，是一个省钱方向。
- **127 秒里大部分是在等模型写字。** 二十多次调用，每次写几百个 token，按每秒 45 个算就是几十秒，再加上工具调用的时间。

这一节的数字来自 `data/oncall_facts.json`，是从项目的评测平台导出的。

## 做项目时

- 每次调用都记下 token、花费、时延，能按调用、按任务、按版本汇总。
- 评测和线上都固定并记录模型版本、temperature、seed；比较两个版本时，这些设置要一样。
- 估算成本按“多轮累计的输入”算，不要按单次调用算；关注缓存命中率，不变的内容放在提示词前面。
- 要交给程序处理的输出，一律检查 finish_reason、用程序校验格式，失败了重试或兜底。
- 事实必须来自工具返回的数据；结论里的引用，由程序核对它是否真的存在。

## 面试常问

**temperature 设成 0，输出就完全确定了吗？**

不完全。temperature=0 只是每步选概率最高的 token，但服务端并发计算的浮点误差，会让概率很接近的两个候选偶尔换位，一换后面就跟着变。我实测 qwen-plus 30 次里有 1 次不一样。另外，有的服务不传 seed 时表现得像固定了种子，调高 temperature 也看不到变化。所以评测时要固定并记录这些参数，并且同一用例多跑几遍。

**为什么 Agent 的花费主要在输入上？**

因为模型无状态，Agent 每一步都要把之前的对话和工具结果重新发一遍。我的项目里一条用例调模型二十多次，单次上下文峰值只有约 7,000 token，累计输入却有 11 万，占全部 token 的 95%。所以省钱的重点是缓存和控制上下文，而不是让回答写短一点。

**怎么减少 Agent 的幻觉？**

一是让事实来自工具，结论只能引用查到的数据。二是由程序核对引用，编号不存在就拒绝提交。三是允许它说“不知道”，在输出格式里留出“还缺什么信息”的位置。我的项目里，子 Agent 在调用失败时还会给失败结果编证据号，复刻集 90 次运行里出现了 10 次；但提交结论时程序会核对编号，最终结论里一次都没有。

## 自测

1. 同一段意思，中文和英文哪个占的 token 多？为什么 JSON 和日志特别占 token？
2. 首字时间和总时间分别主要由什么决定？
3. 为什么 Agent 的累计输入 token 会远远超过单次调用的上下文长度？
4. temperature、top_p、seed 各控制什么？为什么不传 seed 时，把 temperature 调高也可能看不到变化？
5. temperature=0 还会出现不同输出的原因是什么？这对评测 Agent 意味着什么？
6. finish_reason 等于 length 说明什么？等于 stop 就能保证输出可用吗？
7. 子 Agent 给失败的调用编上证据编号，属于什么问题？这个项目靠什么挡住它？
