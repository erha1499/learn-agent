# 单元二十三 上线以后：分诊、回流、SLO、出事时怎么办

本单元的核心：上线以后的工作是一个循环：用线上信号和随机抽样找出失败，按机制分类，挑最大的一类转成评测题，修，过门禁，再上线看效果。每转一圈，信号看得见的那类错会变少，剩下的往往是信号看不见的，所以随机抽样不能停，信号也要跟着补。质量目标写成 SLO，靠每周随机核对来量；出事的时候按预案先止血，再查原因。

**学完这个单元，你能：**

- 跑通一次“发现、分诊、入库、修复、门禁、验证”的循环，说清每一步做什么、用什么数据。
- 判断一次修复有没有起作用：按失败的类型、按题配对来比，不看总数；知道修完以后信号为什么会变瞎。
- 为 Agent 定 SLO 和错误预算，算出质量 SLO 每周要核对多少个会话；写出常见事故的处置预案。

单元十九讲了上线以后能看到哪些信号、怎么抽样、怎么盯变化；单元十四讲了线上失败怎么变成新题；单元二十二讲了门禁和灰度。本单元把它们串成一圈，在骨架上真的转一次：一周的线上流量，分诊，入库，修，过门禁，再看第二周。然后讲 SLO 和错误预算、出事时的预案，以及下一圈改什么。

## 23.1 先看现象：第一周

跑 `examples/u23_loop.py`，全部用单元二十一的骨架跑。线上流量每周 100 个会话，问题从 30 道里随机抽：迷你评测集的 20 条，加上单元二十“换说法”的 10 条；28% 的会话碰上错误日志服务抖动，第一次调用超时。第一周是 v1，也就是单元十三的 Agent。

| | 第一周 |
|---|---|
| 真实情况（线上看不到） | 答对 80，答错 20 |
| 代码信号标记（单元十九） | 35 个，其中真错 9 个 |
| 随机抽 25 个核对 | 错了 5 个，答错率估计 20%（95% 区间 9% ～ 39%） |
| 运行指标 | 平均调工具 3.7 次，工具报错率 10%，每个会话 3,798 token |

把标记的和随机抽的合起来人工核对（这里用真实标签模拟），一共 44 个会话，找到 12 个答错，占这一周全部答错的 60%。另外 40% 没被看见：它们既没被信号标出，也没被抽中。

## 23.2 分诊：按机制分类，挑最大的一类

核对出来的 12 个答错，按“错在哪一步”分类：

| 类型 | 个数 | 例子 |
|---|---|---|
| 某个数据源报错后再没成功过，Agent 拿剩下的证据下了结论 | 8 | C13 碰上超时，答成锁等待；V08 碰上超时，答成慢 SQL |
| 一次工具没调就下结论 | 1 | C15：转发的消息让它跳过取证 |
| 其他：数据都拿到了，推理错了 | 3 | C06：慢 SQL 把连接拖满，答成连接数打满 |

第一类最多，而且原因清楚：单元十九见过，数据源一出错，Agent 不会说“查不到”，而是凑一个结论。它也最好修，修法写得成程序规则：

- **工具超时，程序自动再调一次**，不靠模型想起来重试；
- **交卷时检查关键证据**：结论对应的数据源一次都没成功返回过，就改成“不知道”、转人工（单元二十的门）。

两条都是骨架里的配置开关（`harness.tool_retry`、`harness.key_evidence`），打开以后配置指纹变了，v1 的 `f2a339b8fe0b` 变成了 v2 的 `b544322d3596`。第三类推理出错，暂时不修：它的原因各不相同，修法也不确定，留给下一圈（23.7）。

分类用的是能从轨迹里直接判断的特征：有没有调过工具，有没有某个工具报错后再也没成功。一个分类规则能写成代码，下一周就能自动统计这一类有多少。

## 23.3 入库、修、过门禁

**入库。** 评测集从 20 条扩成 40 条：原来的 20 条，换说法的 10 条，再加 10 条“错误日志第一次超时”的版本（原来 plain 和 distract 难度的 10 条用例，换成会超时的环境）。线上出现过的失败方式，评测集里都要有（单元十四）。

**过门禁。** v1 和 v2 在新评测集上各跑 3 遍，用单元二十二的门禁判：

| | 答对 | 答错 | 转人工 | 每次 token | 耗时 p90 |
|---|---|---|---|---|---|
| v1 | 87% | 13% | 0% | 3,808 | 15.7 秒 |
| v2 | 88% | 9% | 3% | 3,727 | 16.5 秒 |

按题组拆开，对 / 错 / 转人工：

| 题组 | v1 | v2 |
|---|---|---|
| 原来的 20 条（共 60 次） | 54 / 6 / 0 | 51 / 5 / 4 |
| 换说法的 10 条（共 30 次） | 26 / 4 / 0 | 27 / 3 / 0 |
| 超时版本的 10 条（共 30 次） | 24 / 6 / 0 | 27 / 3 / 0 |

门禁结论是通过：没破底线，没做坏回归题，答错率比 v1 低 4.2 ± 9.7 个点。区间包含 0，评测集上看不出显著的提升；但改进集中在超时版本上，6 个答错变成 3 个，正是这次要修的那一类。原来 20 条里多出来的 4 次转人工，3 次是 C15 被门拦下了：一次工具没调就下的结论，现在交给人；另 1 次是 C11，结论对了，可它没查过锁等待对应的慢查询日志和错误日志，门照样转给了人，这是单元二十说过的代价。

## 23.4 第二周：修好了一类，信号也瞎了一块

第二周上线 v2，换一批随机会话，同样 100 个、28 个碰上超时。

| | 第一周 v1 | 第二周 v2 |
|---|---|---|
| 答错（线上看不到） | 20 | 17 |
| 其中：数据源报错后凑结论 | 8 | 0 |
| 其中：一次工具没调就下结论 | 1 | 0 |
| 其中：推理出错 | 11 | 17 |
| 转人工 | 0 | 2 |
| 工具报错率 | 10% | 0%（程序自动重试了 37 次） |
| 代码信号标记 | 35 个，真错 9 个 | 3 个，真错 0 个 |
| 随机抽 25 个估的答错率 | 20%（9% ～ 39%） | 12%（4% ～ 30%） |

读这张表抓住三点：

- **要修的那一类修好了。** 数据源报错后凑结论的，从 8 个变成 0 个；注入那一条被门拦下，转了人工。
- **总数只少了 3 个，因为流量的组成变了。** 出过推理错误的那几道题，第一周抽到 36 次，第二周 46 次。按题配对比（两周都出现过的 28 道），第二周的答错率低 10.3 ± 12.6 个点。看一次修复有没有用，要按失败的类型、按题配对来比，不看总数（单元十七、十九）。
- **信号瞎了一块。** 第二周剩下的 17 个答错全是推理出错，代码信号一个都没标出来；它标出的 3 个会话里，2 个是被门拦下的 C15，1 个答对了。代码信号看得见的那类错修掉以后，剩下的正是它看不见的。只有随机抽样还能看见它们：25 个里错了 3 个。所以随机抽样不能停，还要补上看得见推理错误的信号，比如单元十九的评委和重跑一致性。

## 23.5 SLO 和错误预算

把质量目标写成 SLO（服务等级目标），每个时间窗口量一次：

| SLO | 怎么量 | 例子 |
|---|---|---|
| 可用 | 任务跑完、没有报错退出的比例 | 不低于 99.5% |
| 时延 | 任务完成时间的 p95 | 不超过 60 秒 |
| 质量 | 每周随机核对的答错率，看 Wilson 区间的上限 | 不超过 10% |
| 安全 | 越权、外发事件 | 0 次 |
| 成本 | 每个会话的 token | 不超过 6,000 |

前两项和后两项从轨迹里自动算；质量这一项要人核对，而核对的量决定你能不能证明它达标。用 Wilson 区间算：

| 真实答错率 | 区间上限压到 10% 以下，每周要随机核对多少 |
|---|---|
| 5% | 约 127 个 |
| 8% | 约 830 个 |

反过来，每周只核对 25 个、错了 2 个，区间是 2% 到 25%，什么也证明不了；核对 100 个、错了 10 个，区间是 6% 到 17%。核对不了那么多，就把窗口拉长（比如滚动四周合起来算），或者把 SLO 定在你核对得起的水平上。

**错误预算**是 SLO 剩下的余量：质量 SLO 是答错率不超过 10%，这个窗口估出来是 6%，还剩 4 个点可以“花”在有风险的改动上。预算花完了（估出来超过 10%），就暂停新功能，先修可靠性。这个做法来自 Google 的 SRE 实践，用在 Agent 上，就是把“改提示词、加工具”的速度和线上质量绑在一起：质量掉下来，改动先停。

## 23.6 出事的时候

Agent 的事故，先止血，再查原因，最后把它变成评测题或回归用例。几类常见的：

| 事故 | 先看到什么 | 先做什么 | 之后做什么 |
|---|---|---|---|
| 模型服务出故障或限流 | 429 和 5xx 的比例、排队长度、耗时（单元二十一） | 网关切到备用模型或只读模式；告诉用户在排队 | 查上游状态；失败的任务从事件日志重放 |
| 发布后质量下降 | 灰度或全量后过程指标变了、用户反馈 | 改指针回滚（单元二十二） | 查门禁为什么没挡住，补评测题 |
| 数据源出错 | 工具报错率（单元十九） | 程序重试，查不到就转人工，不让 Agent 凑结论 | 修数据源；加对应的超时用例 |
| 注入攻击 | 外发被拦截的次数、出现陌生的频道或地址 | 程序白名单本来就挡着（单元十一、十八）；收紧权限 | 把攻击写法加进安全回归集 |
| 成本突然涨 | 每个会话的 token、单个会话的轮数 | 预算上限截停（单元十二） | 查是不是死循环、上下文膨胀 |
| 模型要退役 | 服务商的弃用通知 | | 退役之前跑门禁，选好替代者（单元二十二） |

单元十二讲过的两次复盘，都是用户先察觉的。之后 Anthropic 在真实的生产系统上持续跑质量评测、把用户反馈当成连续的信号，并且让内部员工用和用户完全一样的版本。预案里“先看到什么”这一列，就是在问：这类事故，你能不能比用户先知道。

## 23.7 下一圈改什么

第二周剩下的都是推理错误：慢 SQL 把连接拖满时答成连接数打满，换了说法的证据读错了。可选的改法：

| 改什么 | 适合 | 这次的情况 |
|---|---|---|
| 程序规则（harness） | 必须守住的硬要求：重试、证据、权限 | 第一圈已经用了 |
| 提示词 | 偏好和领域提示，比如“连接数打满时先看是不是慢 SQL 拖的” | 可以试；单元二十二里“最多查两个数据源”那句就做坏了三道回归题，提示词改动的副作用要靠门禁看 |
| 换模型 | 剩下的错误是能力问题 | 单元二十二的门禁里，qwen3.7-plus 在原来 20 条上答对 100%，耗时 p90 高一些 |
| 补信号 | 现在的信号看不见的那类错 | 评委、重跑一致性（单元十九），先让下一周看得见 |

几条原则：

- **先补信号，再修。** 看不见的错没法分诊，也没法验证修好了没有。
- **一圈只修一类，修法尽量写成程序规则。** 程序规则行为确定、好测，提示词改动的副作用要靠门禁才看得出来。
- **每一圈都过门禁、灰度，修完看第二周。** 评测集上看不出显著的提升，不代表没用；按失败类型去看线上的变化。
- **节奏要固定。** Anthropic 2026 年 1 月的《Demystifying evals for AI agents》建议持续处理用户反馈、每周抽一批轨迹来读；评测集“越晚建越难建”，每一圈线上失败都要回流成题。

## 做项目时

- 上线以后按固定节奏转圈：发现、分诊、入库、修复、门禁、验证。
- 复核分两路：信号标记的用来找错，随机抽的用来估水平、看见信号看不见的错。
- 失败按机制分类，分类规则写成代码，下一周自动统计；一圈只修最大、最清楚的一类。
- 线上出现过的失败方式，评测集里都要有对应的题；修复走门禁和灰度。
- 看修复效果按失败类型、按题配对比，不看总数；流量的组成每周都在变。
- 修完一类，补一个能看见剩下那类错的信号。
- 定 SLO：可用、时延、质量、安全、成本；质量靠随机核对，核对的量要够证明它达标；用错误预算决定什么时候暂停新功能。
- 为常见事故写好预案：先看到什么、先做什么、之后做什么；回放事件日志，把事故变成评测题。

## 面试常问

**Agent 上线以后怎么持续改进？**

转一个固定的圈：线上信号标出可疑的会话，再随机抽一批，人工核对；答错的按机制分类，挑最大、最清楚的一类，把这种失败方式加进评测集，修，过门禁，灰度上线，下一周按类型看它少了没有。我在一个值班 Agent 上转过一圈：第一周 100 个会话答错 20 个，核对出来最大的一类是数据源超时后 Agent 拿剩下的证据凑结论；修法是两条程序规则，超时自动重试、交卷检查关键证据。第二周这一类从 8 个降到 0。

**怎么知道一次修复有没有起作用？**

按失败类型、按题配对来比，不看总数。我那次修复后，总的答错只从 20 降到 17，因为第二周的流量里难题多了：出过推理错误的题从 36 次变成 46 次。按题配对，答错率低了 10.3 ± 12.6 个点；按类型看，要修的那类从 8 个变成 0。还有一个坑：修完以后，代码信号标出的 3 个会话一个答错都没有，剩下 17 个推理错误它全看不见，只有随机抽样还看得到。所以修完一类，要补一个能看见剩下那类的信号。

**Agent 的 SLO 怎么定？质量怎么量？**

可用、时延、安全、成本从轨迹里自动算；质量要靠每周随机核对，看答错率的 Wilson 区间上限。核对量决定能不能证明达标：真实答错率 5% 时，要核对约 127 个，区间上限才压得到 10% 以下；每周只核对 25 个，区间宽得什么也证明不了。核对不了那么多，就拉长窗口或者把目标定在核对得起的水平。再配一个错误预算：估出来超过 SLO，就暂停新功能，先修可靠性。

**线上出事了怎么办？**

先止血，再查原因，最后变成评测题。模型服务故障就让网关切到备用模型或只读模式；发布后质量下降就改指针回滚；数据源出错就让程序重试、查不到转人工，别让 Agent 凑结论；注入攻击靠程序白名单兜底，再把攻击写法加进安全回归集；成本暴涨靠预算上限截停。关键是每类事故都要有一个比用户先看到的信号。

## 自测

1. 第一周的 100 个会话里，真实答错多少？代码信号和随机抽样各找到多少？有多少答错谁都没看见？
2. 核对出来的答错分成哪几类？为什么先修“数据源报错后凑结论”这一类？修法是什么？
3. 评测集怎么扩充？门禁的结论是什么？为什么区间包含 0 也说明修复起了作用？
4. 第二周总的答错只少了 3 个，为什么？怎么比才看得出修复的效果？
5. 修完以后，代码信号为什么“瞎了”？该怎么办？
6. Agent 的 SLO 包括哪几项？质量 SLO 每周要核对多少个会话？核对不了那么多怎么办？
7. 什么是错误预算？用在 Agent 上是什么意思？
8. 模型服务故障、发布后质量下降、数据源出错、注入攻击，各先做什么？下一圈该改提示词、harness、模型，还是补信号？
